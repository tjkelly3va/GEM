## Purpose

Systematic extraction of **structured, codeable data** from Medicare coverage policy documents (NCDs, LCDs, and MCD Articles) into the GEM ontology. The goal is to standardize the data found in a policy so it can later be used to suggest which policies are relevant to a Medicare claim under analysis.

This skill prioritizes **accuracy over speed**. A wrong ICD-10 code, an inverted coverage polarity, or a falsely-empty coding section is a real-world error in a Medicare-claims ontology. Every methodology rule below exists to prevent a specific, documented failure.

**What "structured data" means here:** diagnosis codes, procedure/item codes, procedure modifiers, provider credentials, the policy-to-policy reference links that connect them, and clinical concepts. Clinical concepts — clinical, physiological, diagnostic, therapeutic, and equipment concepts named in policy text — are extracted as `gem:ClinicalConcept` individuals linked to the policy, whether or not they carry a code (see "Clinical Concepts"). This replaces the earlier approach of routing prose concepts to a worklist for future coding.

## Core Principles

1. **Close reading, not pattern matching.** Read the whole policy. Codes hide in prose, in tables, and in revision history — and those three contexts mean different things (see "The Three Code Contexts").
2. **Never guess a code.** Never infer, construct, or assign an ICD-10 or HCPCS code the document does not literally state. If prose names a clinical concept but gives no code, the concept is still captured — as a `gem:ClinicalConcept` individual (see "Clinical Concepts") — but no code is invented for it.
3. **Polarity is per-code, from local context.** Whether a code is *covered* or *non-covered* is read from the sentence or table heading governing that specific code — never assumed from the document as a whole.
4. **A gate is a hard stop.** If any section of the policy is license-gated (renders "Please accept the License to see the codes" or equivalent), stop immediately, do not produce a partial Plan, and request a complete PDF of the policy from the user. A "N/A" section in an otherwise complete document is confirmed empty; a *gated* section is withheld content and the document is incomplete. See "The Gate Hard-Stop Rule."
5. **Extend before inventing.** Reuse existing GEM terms. Propose a new term only when no existing term fits, and only with user approval.
6. **Two outputs per discovered policy reference.** A referenced policy produces both a graph link (`gem:referencesPolicy`) and a worklist entry (processing status). They are complementary, not redundant.
7. **Honest reporting.** If a policy was not fully read, say so explicitly. A plan presented as complete but based on partial reading is worse than one clearly marked incomplete.
8. **Source-fidelity over query convenience.** Write triples that reflect what the source actually asserts, at the structural level the source asserts them, with provenance. Do not synthesize aggregate or projection claims the source itself never makes, even when the synthesized claim would be true and convenient for queries. (Detail: §Extraction Taxonomy / The source-fidelity principle.)
9. **One question at a time.** When a Plan turn, a checkpoint review, a skill refinement, or any other interaction surfaces multiple borderline decisions requiring user judgment, work through them iteratively — one question per response, awaiting the user's answer before asking the next — rather than bundling. Bundling forces the user to track several unrelated decisions at once; sequential approval preserves attention on each decision and yields better calls. The structured artifact (manifest, refinement proposal, checkpoint summary) still presents all decisions in one place; it is the *conversational approval* that proceeds one-at-a-time.
10. **Policies as jigsaw puzzle pieces.** Silence in a single policy on a scenario it might be expected to address is *incompleteness*, not negation. Extraction does not fabricate rules for scenarios the source is silent on, even when parallel treatment seems expected; the rule's scope is exactly what the source asserts. The complete picture emerges from combining rules across policies — downstream resolves both *differences* (via §Rule Patterns → "What belongs as a rule" corollary #3, the verbatim-capture posture) and *gaps* (via this principle). The cross-policy corollary of #8 (source-fidelity is silent on cross-document inference; jigsaw answers: none). (Principle articulated 2026-06-16, Session 63, by Tom: *"Policies may not tell you how to handle something that they just discussed. Policies can be like jigsaw puzzle pieces — they are not the complete picture. But if we combine the rules from multiple policies, we may get a more-complete picture."*)

11. **Umbrella class or property for shared conceptual roles.** When extending the schema with new terms that share a common conceptual role — e.g., they form an axis of values, a qualifier kind, an applicability dimension — prefer introducing a single umbrella over treating each new term as standalone. The umbrella may take any of three structural shapes: an abstract parent class (with sub-classes), an abstract parent property (with sub-properties), or a concrete class typed onto controlled-vocab individuals. **Elevate only when the umbrella has operational utility** — queryable (SPARQL distinguishes the axis from arbitrary grouping), validation-targetable (SHACL or an audit check references the umbrella as a constraint), or otherwise operationally distinguished from "convenient grouping." Without operational utility, the umbrella is naming-for-naming's-sake and should be rejected (cf. S68 Decision 6's rejection of `gem:RuleCategory`). Confirming applications: `gem:AnchoredCodingScope` (S60, class hierarchy); `gem:CoverageQualifier` (S69, class hierarchy); polarity-neutral parent properties (multiple sessions, property hierarchy); `gem:appliesWhenCode` (S70, property hierarchy); `gem:RuleDomain`, `gem:RuleType`, `gem:NextPlannedStep` (S71, typed controlled-vocab individuals). Refines #5 "Extend before inventing" — when invention is unavoidable, this principle governs the *shape* of what you invent.

## The Three Artifacts

This skill governs three files. Know which one each piece of information belongs in.

| Artifact | Path | Contents | Modified |
|----------|------|----------|----------|
| **GEM schema** | `GEM_ontology.ttl` | Classes, properties — the ontological vocabulary. | Only to add genuinely new terms, each approved by the user first. Most policies add zero terms. |
| **Policy instances** | `GEM_policy_instances.ttl` | `gem:CMSpolicy` instances and their reference triples (to diagnoses, procedures, modifiers, credentials, other policies). | Grows with every policy processed. |
| **Worklist** | `policy_worklist.json` | Two lists: related policies to analyze, and deferred schema-extension proposals. (A third list, uncoded clinical-concept prose, was retired when the clinical-concepts category was introduced — see "Clinical Concepts.") | Updated every Generate turn. See `worklist_schema.md`. |

The schema file and the instances file are kept **separate**. Instance data never goes in `GEM_ontology.ttl`; schema terms never go in `GEM_policy_instances.ttl`.

The `owl:versionInfo` value on `gem:gemOntology` is **user-controlled** — it records Tom's published-to-leadership state and must not be edited without his direct request. The value persists across sessions unchanged.

## Document Types

Every policy is one of three types. Each is modeled as a **subclass of `gem:CMSpolicy`** (`gem:NCDpolicy`, `gem:LCDpolicy`, `gem:ArticlePolicy` — established terms in `GEM_ontology.ttl`):

| Type | Subclass | How to identify | Where codes usually live |
|------|----------|-----------------|--------------------------|
| **NCD** — National Coverage Determination | `gem:NCDpolicy` | URL `…/ncd.aspx`; has Publication Number, Manual Section. National scope. | Almost none — NCDs state coverage in prose. Codes live in related Articles/Transmittals. |
| **LCD** — Local Coverage Determination | `gem:LCDpolicy` | URL `…/lcd.aspx`; has LCD ID `L#####`, MAC contractor(s), jurisdiction. | Few. For DME MACs, CPT/HCPCS may remain in the LCD; ICD-10 has moved to Articles. |
| **Article** — MCD Article (esp. Billing & Coding) | `gem:ArticlePolicy` | URL `…/article.aspx`; has Article ID `A#####`; "Article Type" field. | Most. Billing & Coding Articles carry the ICD-10 tables and HCPCS code lists. |

**Why Articles matter most:** the structured data you most want is frequently *not* in the NCD or LCD. NCDs explicitly exclude claims-processing codes; LCDs have largely moved codes out. The Article is where diagnosis tables and HCPCS lists live. The worklist is therefore the primary mechanism by which the ontology acquires codes — treat Article references as high-priority worklist items.

Each instance records, at minimum: identifier (e.g., `NCD 240.2`, `L33797`, `A52514`), document type, title, current version/revision, effective date, and the stable source URL. Capture **current-version metadata only**; route revision history to the worklist's historical list (see below).

## Policy-to-Policy References

Policies cite each other, and those citations are how structured data connects across the corpus: NCD 240.2 → LCD L33797 → Article A52514. The skill captures every such reference **twice**:

1. **As a graph link** — a `gem:referencesPolicy` triple from the citing policy instance to the cited policy instance. This is created even when the cited policy has not yet been processed (the object URI is minted as a stub; the cited instance is fully populated later when its turn comes). `gem:referencesPolicy` is an established GEM object property.
2. **As a worklist entry** — added to the related-policies list with status `pending`, unless already `processed` or already listed.

The graph link records the *dependency*; the worklist records the *processing status*. Both come from the same discovered citation. When a policy is later processed, flip its worklist status to `processed` — do not delete the entry, and do not re-add it.

**Linking direction: which side asserts what.** The policy-to-policy graph uses two predicates with distinct direction rules. The schema declares `gem:revisesPolicy rdfs:subPropertyOf gem:referencesPolicy`, so every revision-direction triple entails (under rdfs:inferencing) a corresponding reference-direction triple in the same direction; both predicates can also be asserted on opposite sides for the same pair of policies.

1. **`gem:referencesPolicy` is asserted on the citing side.** When a policy cites another document in its current-section text — a transmittal in the Transmittal Information field, an NCA in the National Coverage Analyses section, a PM in Claims Processing Instructions, another NCD in Related National Coverage Documents — the citation triple lives on the citing policy's instance. The cited document does not assert a back-link.

2. **`gem:revisesPolicy` is asserted on the revising side.** When a transmittal revises an NCD/LCD/Article (changing its text, adding a section, deleting one), the revision triple lives on the transmittal stub: `gemi:tn<NN> gem:revisesPolicy gemi:ncd<X>`. The same predicate also chains successor transmittals to their predecessors (`gemi:tn<successor> gem:revisesPolicy gemi:tn<predecessor>`). The revised entity does not assert a back-link.

   **The transmittal-edge rule (Tom, S151) decides which predicate.** The transmittal→policy edge is **`gem:revisesPolicy` if the transmittal describes ANY change to the policy — New, Change/Revision, or Delete** — and **`gem:referencesPolicy` if it merely mentions the policy**. Read the change verb, not the version arithmetic. **A transmittal that CREATES a section takes `revisesPolicy`**: "New" is a change. This is the rule's sharp edge and it is deliberate — before S151 the corpus was split 6–6 on exactly this question (six V1 NCDs carried an inbound edge from their deliverer, six did not), because a V1-creating transmittal was read as having nothing to revise. That reading is retired; the split is closed. Worked example (S151, NCD 240.1): `tn83CIM` created the section → `revisesPolicy`; `tn102CIM` changed noncoverage to coverage → `revisesPolicy`; `tn3NCD` expanded coverage → `revisesPolicy`; `tn44NCD` modified facility requirements → `revisesPolicy`; `tn768CP` carries Claims Processing Instructions and the policy's rendition does not describe it as changing anything → `referencesPolicy`. **The rule keys on a described change, not a mention (S169 sharpening, Tom):** a transmittal that merely *names* a policy takes `gem:referencesPolicy`; `gem:revisesPolicy` is asserted only where the transmittal's own record *describes a change it makes to that policy*. Two consequences the S169 `deferred_proposals[99]` backfill turned on: (a) a **quarterly ICD-10 coding-maintenance transmittal that states "no policy change"** is a mention → `referencesPolicy`, never `revisesPolicy` (the code change is a revision-history change-log artifact GEM does not capture; see the three-contexts rule); (b) a **deliverer named only in the Transmittal Information field, with no described change**, is a mention until its own extraction confirms what it changed. **The pre-S151 corpus was backfilled to this rule at S169** (`deferred_proposals[99]` `complete`): of 103 pre-S151 policy→transmittal `referencesPolicy` pairs lacking the transmittal→policy reciprocal, **21** took `gem:revisesPolicy` and 82 stayed `referencesPolicy`. The signal is the section-of-citation recorded in each stub's `gem:description`; it is **not a graph predicate**, so the classification is a close read, not a regex (every keyword scan mis-swept `tn768CP`, this rule's own `references` example). New extractions comply by construction. The standing regression guard is `gem_audit.py`'s `revises_references_redundancy` check (a subject may not assert both predicates to the same object — `revises` entails `references` via subPropertyOf; precedent `tn48NCD → ncd210.2`, removed S169).

3. **`gem:revisedByPolicy` (the inverse of `revisesPolicy`) is never asserted in the file.** The schema defines the inverse predicate (`gem:revisedByPolicy owl:inverseOf gem:revisesPolicy`) and the reasoner materializes it from `revisesPolicy`. **This depends on an OWL profile, not RDFS** — `owl:inverseOf` is outside RDFS entailment, so under an RDFS-only ruleset the predicate is inert rather than inferred. GEM targets an OWL reasoner (Tom, S148); see `gem_reference.md` §7. Contrast the `subPropertyOf` entailment above, which is RDFS and holds under any profile. Asserting both creates redundant maintenance burden and risks drift if one direction is updated and not the other. Likewise, the transmittal→policy direction of `referencesPolicy` is inferred (via the subPropertyOf chain) from `revisesPolicy`, not asserted directly.

4. **The two predicates co-exist when applicable.** When a transmittal is named in a policy's current Transmittal Information field AND the transmittal substantively revises that policy, both directions are asserted (on opposite sides): NCD → TN via `referencesPolicy` on the NCD instance; TN → NCD via `revisesPolicy` on the TN stub. The two assertions are independent: a policy may reference a transmittal that does not revise it (e.g., a Claims Processing Manual transmittal cited in Claims Processing Instructions), and a transmittal may revise a policy that does not yet cite it (e.g., a successor transmittal not yet reflected in the MCD page). Example of both: NCD 230.18 → TN 144 via `referencesPolicy`; TN 144 → NCD 230.18 via `revisesPolicy` (S50 first extraction).

The convention is empirically verified: as of S260, 240 `gem:revisesPolicy` assertions exist (all on transmittal-side subjects), 0 `gem:revisedByPolicy` assertions exist, and 1119 `gem:referencesPolicy` assertions exist (all on citing-side subjects; the transmittal-side `referencesPolicy` direction is inferred via subPropertyOf rather than asserted). (Rule codified 2026-06-12, Session 50, after S50 NCD 160.7 reprocessing initially omitted the NCD-side `referencesPolicy` link for TN 78; the omission was corrected in S51 §4.2(v) backfill.)

**Superseded revisions earn no reciprocal (three-contexts corollary).** *[Updated S131: superseded for the `referencesPolicy` direction by the mint-every-referenced-policy rule — the citing policy now asserts an agnostic `gem:referencesPolicy` to* every *transmittal it names, superseded revision-history transmittals included. The rule below now governs only the stronger `revisesPolicy`/reciprocal direction (asserted post-analysis), not whether a citing-side `referencesPolicy` exists.]* When a transmittal revised an *earlier* version of a policy that a newer transmittal has since superseded — the newer transmittal being the policy's current Transmittal Information field entry and carrying the reciprocal `referencesPolicy` — the older transmittal's `revisesPolicy` link is preserved as revision-lineage provenance but earns **no** citing-side `referencesPolicy`. Per the three-contexts rule a Revision-History transmittal is not a current reference, and (§Policy-to-Policy rule 4) the reciprocal is asserted only for the transmittal in the *current* Transmittal Information field. The link is not removed either — absent a current statement that the transmittal is inapplicable, a genuine past revision stays (see §"removing a link"→ removal is reserved for wrongly-scoped current-prose links, not historical facts). `gem_audit.py`'s `check_proposal_b` classifies this as **Category E (superseded-revision, GREEN)**, distinct from a Category D extraction gap; a lone unreciprocated `revisesPolicy` with no current transmittal still returns Category D (RED), so genuine gaps like the S50 TN 78 omission are not masked. (S107; precedent: `tn48 revisesPolicy ncd20.29`, superseded by `tn203` which ncd20.29 reciprocates.)

**Where references appear:** "Related Local Coverage Documents", "Related National Coverage Documents", "CMS National Coverage Policy", "Sources of Information", and inline prose ("refer to the … LCD-related Policy Article (A52514)", "see §280.1"). Read all of these. Also capture NCAs/CALs and Transmittals as references, but type them accurately: transmittals revising a coverage policy are typed `gem:TransmittalPolicy` at first citation and queued for full extraction (see §Transmittals); NCAs and CALs remain pointer-class artifacts that the user decides later whether to process.

**Stub labeling: the cited policy is authoritative for its own identity.** A citing policy sometimes uses a colloquial or stale label for the section it references. NCD 280.1's "Elastic Stockings" entry cites §270.5, whose actual CMS title is "Porcine Skin and Gradient Pressure Dressings"; its "Lymphedema Pumps" entry cites §280.6, whose actual title is "Pneumatic Compression Devices"; its "Self Contained Pacemaker Monitors" entry cites §280.2, whose actual content is "White Cane for Use by a Blind Person" (the §280.2 citation is stale — the real Pacemaker Monitors NCD is §20.8.2, which 280.1 does not cite directly). In every such case, the cited policy is the authoritative source for its own `gem:prefLabel`. The stub uses the CMS title; the citing policy's colloquial label or stale cross-reference is recorded in `gem:description` as a discoverable data observation. Do **not** mint stubs for what the citing policy *should have* cited but didn't (no §20.8.2 stub from 280.1's misdirection) — faithfulness to what the source actually says is the rule, even when the source is wrong. The mis-labeling itself is a finding worth preserving in description prose, not an error worth correcting in the cited stub's identity.

**Resolving URLs for cited policies that Claude does not already have.** Every cited-policy stub minted in the graph carries `dc:source` as a real document URL (per `gem_turtle_style_guide.md`). When the citing policy introduces a cited policy whose URL is not already on hand, Claude resolves it via web search rather than blocking. The procedure:

1. **Search.** Query the CMS Medicare Coverage Database for the cited policy. Only `cms.gov` URLs are eligible as `dc:source`. URLs from other domains (HHS guidance repository, NCA aggregators, vendor pages, third-party summaries) never become `dc:source`, even if they rank higher in search results.
2. **Verify by fetch.** Open the candidate URL and confirm that (a) the policy identifier matches the citation (section number or CAG ID), (b) the document type matches (NCD / NCA / LCD / Article / Transmittal), (c) the title is plausible. If any of the three fails, treat the candidate as a search miss.
3. **Batch and present (informational).** At the end of the Plan turn, present the list of `{identifier, found URL, verification snippet}` for any web-resolved URLs as an informational block. The user may override or correct at any time. Explicit per-URL approval is not required when step 2's three verifications (identifier match, type match, title match) all pass cleanly — the stub's tentative URL is confirmed at the cited policy's own Plan turn per the "Confirming a URL when a worklist entry begins processing" paragraph below. Step 4 (search miss or ambiguity) still requires user escalation.
4. **On search miss or ambiguity.** If the search returns nothing usable, or returns multiple plausible candidates and verification cannot disambiguate, either (i) present the candidates to the user to pick from, or (ii) ask the user to supply the URL outright. Both are preferable to omitting `dc:source` or inventing a URL.
5. **Annotate provenance.** Stubs whose URL came from web search rather than the user carry a marker phrase appended to `gem:description`: *"URL resolved by web search and user-verified at extraction time."* User-supplied URLs need no such marker (this is the default and matches all stubs minted before this protocol).

**Confirming a URL when a worklist entry begins processing.** When a `pending` entry moves to active processing (its own Plan turn begins), Claude requests the URL from the user at the start of the turn. The user-supplied URL takes precedence over any URL already stored on the worklist or on the existing stub. If the supplied URL differs from the stored URL, Claude shows the delta and asks whether this is a URL correction (update only — refresh `source_url` on the worklist entry and `dc:source` on the stub) or a different policy entirely (rebuild the stub from the new URL, including its `gem:identifier`, `gem:prefLabel`, and `gem:description`). Either way the user's URL becomes canonical.

**Medicare URLs are not canonical; the user's URL is.** CMS does not maintain a public canonical-URL schema for its policy documents. Forms found in the wild — case differences (`?ncdid=` vs `?NCDId=`), version parameters (`&ncdver=N`), breadcrumb-style query suffixes — are coincidences of CMS's web infrastructure at the moment of observation, not a defined standard. Two consequences for the workflow:

- **No URL audits, no normalization proposals.** Claude does not compare new URL observations against existing stubs' URL forms to surface "inconsistencies," and does not propose normalization passes across stubs. Casing or parameter differences across the graph are not findings worth raising.
- **No URLs by analogy.** When Claude needs a URL it does not have, the only resolution paths are (a) `web_search` per the procedure above, or (b) ask the user. Claude does not extrapolate URLs from sibling-document patterns (e.g., constructing a transmittal URL by analogy from another transmittal's URL).

A user-supplied URL — at any point in the workflow — overrides any URL Claude previously stored, on the worklist, on a stub, or from a prior search. Claude refreshes `dc:source` and the worklist `source_url` to the user-supplied form without flagging the prior form as inconsistent.

**Manual-chapter URL publication must match the citing text's named manual (URI-determining exception).** A `gem:CMSmanualChapter` stub's URI local-name encodes the publication number — `gemi:pub100_02_ch<n>` (Pub. 100-02, Medicare Benefit Policy Manual) versus `gemi:pub100_04_ch<n>` (Pub. 100-04, Medicare Claims Processing Manual) — so for these stubs the supplied URL's publication is **URI-determining**, not merely a `dc:source` value. Before minting, verify the URL's implied publication (the CMS PDF prefix names it: `bp102…` = Pub. 100-02; `clm104…` = Pub. 100-04) against the manual named in the citing policy's text. If they disagree, **surface the mismatch and do not silently mint** — the disagreement decides which chapter entity is being created. This is the one carve-out from "No URL audits, no normalization proposals" above: it is not a source-authority, casing, or normalization finding (casing, `&…ver=`, and parameter differences remain non-findings), and it does not generalize to auditing `dc:source` on NCD/LCD/Article/Transmittal stubs, whose URLs are never URI-determining. Once the publication is confirmed consistent, the user's URL is canonical as usual. Precedent (S119, NCD 80.11 → Ch 14): the first supplied URL was `bp102c14.pdf` (Pub. 100-02), but NCD 80.11's text cites the Claims Processing Manual (Pub. 100-04); the mismatch was surfaced and the user corrected it to `clm104c14.pdf`, fixing the URI to `gemi:pub100_04_ch14`.

**Recording cleared discoveries.** A stub's Plan-time description may carry an explicit uncertainty — section identity unverified, title needing confirmation, status flagged — that is later resolved (most often during URL resolution, less often during the cited policy's own extraction or a separate enrichment turn). Clearing such an uncertainty does **not** mean rewriting the description as if the uncertainty never existed. Keep the original uncertainty visible and append the resolution, so a future reader sees both what was once in doubt and how it was settled. Format: `[original uncertainty]. CLEARED [YYYY-MM-DD]: [resolution and method].` Precedent: NCD 20.8.1 was minted at NCD 280.1's Plan time with the note "Section identity unconfirmed (three-level numbering unusual for NCD top-level)"; the same description now records "CLEARED 2026-05-29 via web_search: §20.8.1 is the established NCD 'Cardiac Pacemaker Evaluation Services' (NCDId=160); three-level numbering is normal in the §20.8.x cardiac-pacemaker family." This pattern is symmetric with the URL-from-web-search marker in step 5 above — both preserve provenance for a fact that wasn't certain at Plan time.

**Asymmetric-stub selection — when to mint as ANNOTATION-ONLY STUB.** A cited policy whose content is administrative-only or context-only — not expected to contribute extractable coverage data on its own — is minted as an `ANNOTATION-ONLY STUB` (slot 6 of §File Layout Conventions) rather than a regular `POLICY STUB`. The asymmetric-stub pattern preserves the citation as a resolvable URI without committing the worklist to a future full extraction pass. Established uses from S39: an NCD cites an NCA whose content is the deliberative analysis behind the NCD (CAG-00313R / CAG-00313R2 cited by NCD 160.18); an Article cites the LCD it pairs with (L38276 cited by A58075, with the LCD already in scope as a lead policy); a "see also" NCD cites complementary NCDs whose own coverage is administered separately (NCD 160.2 / NCD 30.1 / NCD 160.7.1 cited by NCD 160.7). The standard `POLICY STUB` remains the default when the cited policy's content is genuinely missing from our scope and a future extraction would add value; choose `ANNOTATION-ONLY STUB` when the absence of a future extraction is the *intent*, not a deferral. The worklist still records the asymmetric stub as a `related_policies` entry — the layout slot and the worklist entry are independent of each other; the layout choice does not exempt the citation from worklist tracking. (Rule established 2026-06-05, Session 40, codifying the S39 asymmetric-stub pattern.)

**Deleted-section stubs.** For stubs minted at `gemi:ncd<section>_DELETED` (or analogous LCD/Article URIs) when a transmittal deletes an entire coverage policy, the conservative cross-reference principle in §Transmittals governs whether a `gem:referencesPolicy` triple is minted — only when the deleting transmittal's prose explicitly grounds a surviving section. The URI convention itself is documented in `gem_reference.md` §5.3.

**One exception:** a policy processed under the "reviewed, no action taken" outcome captures *none* of its own outgoing references **as graph links** — see "The 'reviewed, no action taken' outcome." The two-outputs rule keeps an extracted policy's reference web complete; a deliberate-zero policy has no web to complete. (Worklist surfacing of those same references is a separate, user-decided question — see item 5 of that section.)

**Umbrella articles: the Associated-Documents catalog *is* the reference set (S161).** For most policy articles the Associated-Documents list is a shared cross-index of a device family, and only the article's *in-text* references are captured — the peer A52467 (PAP) links 7 substantive references, not its full catalog. A **cross-cutting umbrella article** — one whose subject is a requirement governing an entire program area rather than a device (a Standard Documentation Requirements article, a coding-authority article) — is the exception: its Associated-Documents catalog *is* its substantive reference set, because the article genuinely applies to every policy listed, and the "applies-to" relation would otherwise only ever accrue from the other side. For such an article, mint the full catalog under the mint-every-referenced-policy rule. Precedent: A55426 (Standard Documentation Requirements), S161 — 118 Associated-Documents entries linked (100 minted as `planPromote` stubs), a deliberate departure from the A52467 precedent. The tell is the article's own scope statement (A55426: "requirements that apply to ALL claims … for any DMEPOS item"). When it is unclear whether an article is an umbrella, surface it as a Plan-turn borderline rather than defaulting either way.

## Transmittals

A transmittal that revises a coverage policy (NCD, LCD, or Article) is itself a policy document — typed `gem:TransmittalPolicy` and extracted from its full PDF through the normal two-turn workflow. This replaces the prior framing in which a transmittal defaulted to a bare `owl:NamedIndividual` pointer and was escalated only when verification failed. (For the direction conventions governing which side asserts `gem:revisesPolicy` versus `gem:referencesPolicy`, see §Policy-to-Policy References → “Linking direction: which side asserts what.”)

**The governing principle.** Codes and clinical concepts are linked to the document that *actually contains* the guidance — never to a document that *should* or *will* contain it. Extraction reads what a document says now, not what a future revision will say. A transmittal whose changes have not yet been folded into its affected manual section IS the document that carries the operative coverage instruction, and the downstream claim evaluator needs to read it. A transmittal whose changes have already landed in the affected section is still a document of record — the change history, issue date, and rationale all live there. Either way, the transmittal is treated as a first-class policy document.

**Operational workflow.**

1. **At first citation**, a transmittal is minted directly as a `gem:TransmittalPolicy` stub (URI `gemi:tn<NN><suffix>`) — never as a bare `owl:NamedIndividual`. It carries `gem:prefLabel`, `gem:description`, and (when known) `dc:source`. It is added to the worklist with `reference_type: Transmittal`, `status: pending`.
2. **When the PDF is available**, the transmittal is extracted through the normal two-turn workflow — read completely, structured-data extracted with polarity and governing text exactly as for any policy. Its worklist `status` flips `pending → processed` and `policies_processed` increments. The transmittal asserts `gem:revisesPolicy` triples to each affected policy (`gem:revisesPolicy` and its inverse `gem:revisedByPolicy` were added to the schema in S41).
3. **A transmittal's reading may yield zero structured-data triples.** When its content is purely prose, or its changes have already landed in the affected policy, the extraction may have no codes or clinical concepts to record. Such an outcome is handled per "The 'reviewed, no action taken' outcome" (see §Policy-to-Policy References) — a deliberate, complete reading whose correct result is zero. The structural `gem:revisesPolicy` triples are always written even when no other content is.

**Content-propagation observation (not a gate).** A transmittal claims a change to one or more affected policies. Whether that change has already been folded into the current text of an affected policy is a finding worth recording — it tells the user whether content-propagation enrichment of the affected policy might be useful — but it does NOT gate the transmittal's typing or extraction. The observation is best-effort:

- **At the citing policy's Plan turn** (when policy P cites transmittal T): if P's current text or another already-extracted policy in the graph clearly reflects T's claimed change, record this. If verification isn't readily possible (T not yet extracted, P's content doesn't speak to the question), record that too. Do not block extraction or hold T pending verification.
- **At T's own extraction**: for each affected policy T revises, observe whether the current text of that affected policy reflects T's change. Report findings to the user as part of T's Plan turn. The user decides whether to direct any content-propagation enrichment of an affected policy. The observation alone does not trigger such enrichment.

The observation is recorded in the Plan-turn manifest's `change_propagation_observation` field on the relevant `policy_references` entry (see `manifest_format.md`). At Generate, the observation is persisted in two places: appended to the transmittal stub's `gem:workflowDescription` as natural-language prose, and appended to the transmittal's worklist `note` field. This makes the observation queryable via SPARQL (text search on the stub's workflow description) and visible during worklist review without requiring a graph query. No *dedicated* change-propagation property is minted — the observation reuses the existing general-purpose `gem:workflowDescription` predicate; promotion to dedicated triples is deferred until the observation data proves load-bearing for downstream queries. **(S166: the persistence pointer moved from `gem:description` to `gem:workflowDescription`, resolving `deferred_proposals[100]`'s fifth scope call — a change-propagation observation is workflow-flavored, and anything workflow-flavored belongs in `gem:workflowDescription`. New extractions comply by construction from S166; the existing in-`gem:description` observations are migrated onto `gem:workflowDescription` in `deferred_proposals[100]`'s own corpus sweep.)**

**Claims Processing Manual transmittals (Pub. 100-04) are minted as `gem:TransmittalPolicy` stubs at first citation, exactly like coverage-manual transmittals (Session 45 methodology revision).** At first mint the stub gets `gem:nextPlannedStep = gem:planPromote` (the workflow-state default) — it awaits full extraction at a future Plan turn. This replaces the prior "out of scope" stance, in which Pub. 100-04 transmittals were recorded as flagged references only. The decision whether to advance any specific Pub. 100-04 transmittal to full extraction is made at its own Plan turn; keeping `gem:planPromote` until then is the default. Program Memoranda — the pre-MAC predecessor publication of transmittals — are minted as `gem:ProgramMemorandumPolicy` stubs (a sibling class of `gem:TransmittalPolicy`, both subclasses of `gem:CMSpolicy`); the same handling applies. Worked example: NCD 240.9's Claims-Processing chain — TN 13374 → TN 13611 → TN 13756 → TN 13808 — each successor `gem:revisesPolicy` its predecessor; the rescinded predecessors carry workflow state consistent with their superseded role.

### Change Requests

A **Change Request (CR)** is the numbered CMS instruction work-item that mandates a coverage, operational, or system update — the "what" and "why." A **Transmittal** is its delivery vehicle (the cover notice summarizing the manual updates and implementation dates). Each CR is assigned a transmittal number on issuance; the two operate as an instruction-and-delivery pair. The CR detail may be carried *within* the transmittal itself, or in a separate referenced file.

A CR is modeled as `gem:ChangeRequest`, a subclass of `gem:CMSpolicy` (sibling of `gem:TransmittalPolicy` / `gem:ProgramMemorandumPolicy`). When an extracted transmittal names a CR, mint the CR as a `gem:ChangeRequest` stub with `gem:nextPlannedStep = gem:planPromote` (full extraction decided at its own Plan turn), and link it with one of two properties:

- **`gem:transmitsChangeRequest`** (transmittal → CR) — the *delivery* relationship: the transmittal carries this CR. Sub-property of `gem:referencesPolicy`; inverse `gem:changeRequestTransmittedBy` (asserted forward-only, like `revisedByPolicy`). One CR may be transmitted by several transmittals across a rescind/replace chain. Assert the edge from **each** delivering transmittal (every-deliverer convention, S131) — the CR node is reused, never duplicated; only its `dc:source` singles out the in-effect deliverer. Superseding the earlier cr8169-era "link only the in-effect vehicle" posture.
- **`gem:referencesChangeRequest`** (policy → CR) — the *mention* relationship: "Further information can be found in CR nnnn" and similar. Sub-property of `gem:referencesPolicy`; no inverse.

**CR sourcing convention:** a transmitted CR's `dc:source` is the **IRI of its delivering transmittal** (not a URL). If that transmittal is not yet in the graph, mint it as a `gem:TransmittalPolicy` stub first (its own `dc:source` is the transmittal PDF URL), then point the CR's `dc:source` at it. Worked example (S95, via TN 2677): `gemi:cr8169` `dc:source` `gemi:tn2677CP`; `gemi:cr8206` `dc:source` `gemi:tn1194OTN` (with `gemi:tn1194OTN` minted as the OTN delivery vehicle, `dc:source` its r1194otn.pdf URL).

**Transmittals with no policy rules.** A transmittal serves many purposes, and a given one may carry no coverage-criteria logic (e.g., a recurring fee-schedule-database update whose code-status changes are already captured via `gem:coversProcedure`/`gem:excludesProcedure`). When the rule-selection test yields nothing, mint **no** `gem:PolicyRule` individuals for it; once the other policy-document requirements are met (identity, `dc:source`, `gem:memberOfOntology`, workflow state, and any code/reference links), mark it **done** (`gem:nextPlannedStep = gem:planDone`). Worked example: TN 2677 (S95) — 0 PolicyRules, `planDone`.

**Examples in the graph (as of S41):** TN 48 (revises 20 NCDs; formally extracted at S41 — metadata + structural revision graph; section bodies pending later sessions), TN 151 (cited by NCD 280.6, full extraction deferred).

**Transmittal-driven section deletions and the conservative cross-reference principle.** A transmittal sometimes deletes an entire coverage policy (NCD/LCD/Article section) rather than only changing it. The deleted policy is minted as a stub with the URI form `gemi:ncd<section>_DELETED` (the URI convention, motivation, and full list of current `_DELETED` stubs live in `gem_reference.md` §5.3).

A deleted-section stub sometimes has content that was migrated elsewhere by the same transmittal. For such cases, the **conservative cross-reference principle** governs whether to mint a `gem:referencesPolicy` triple from the `_DELETED` stub to the surviving section: only assert the triple if the transmittal's prose **explicitly grounds** the migration (specific surviving section named in the transmittal text). Inferred-but-unconfirmed surviving locations are noted in the `_DELETED` stub's `gem:description` prose only, never as graph links.

Worked example from TN 48: §270.1.1 deletion included the prose "content was promulgated in section 270.1," explicitly grounding the link — so `gemi:ncd270.1.1_DELETED gem:referencesPolicy gemi:ncd270.1` is asserted. TN 48's four other deletions (§20.8.3, §150.4, §160.3, §160.11) included no equivalent explicit naming of a surviving location; their `_DELETED` stubs carry plausibility notes in `gem:description` prose only, not as graph links.

(Methodology shift established 2026-06-05, Session 41, on Tom's direction: "A transmittal is a policy document which should be realized from the full document, not just a reference." Replaces the prior "pointer-only by default, escalated only when change isn't reflected" framing. Both TN 48 and TN 151 minted under the new methodology.)

```
python gem_audit.py --files-dir . --autofix
```

`--output-dir` is omitted deliberately: the canonical directory is the working directory and is writable, so autofix edits land in place and `git diff` is the review. There is no upload/output split — that was an artifact of the chat-session workflow this skill was ported from (S260).

### Handoff claim blocks

The handoff-drift check (audit category 11, added in `gem_audit.py` v0.2) addresses a class of bug where a handoff §4 open-item carries a stale framing of the graph state, and the next session executes the item as written rather than re-examining whether its premise still holds. Precedent: the S51 §4.1(ii) item described five fully-extracted articles as "stubs" and proposed a `referencesPolicy` backfill that would have violated the §4f rule; the staleness sat in the handoff across S50, S51, and S52 bootstrap until the bug was caught manually.

The check has two tracks. (Established 2026-06-13, Session 52.)

**Annotation track (always runs).** Every policy-identifier mention in §4 prose — `gemi:<localname>`, `NCD <num>`, `LCD L<num>` or `L<num>`, `A<digits>`, `TN <num>`, `PM <id>`, `CAG-<id>` — is resolved to its `gemi:` URI and a one-line graph-state annotation is emitted: type, `nextPlannedStep`, `isInEffect`, outbound `referencesPolicy`/`revisesPolicy` counts, prefLabel. Annotations render in a dedicated `[HANDOFF ANNOTATIONS]` section after the main findings list. They are informational only — tier INFO — and do not affect the audit's exit code. Reading the annotations alongside the prose surfaces drift naturally: a §4 paragraph that says "as stubs" sitting next to a `planStep=planDone` annotation jumps out.

**Structured-claim track (opt-in, assertion-strength).** A §4 item may embed an HTML-comment YAML block immediately after its prose paragraph, of the form:

```markdown
**(ii) A55426 → 5 Articles `referencesPolicy` backfill.** Five articles in graph as stubs (A52466, ...) lack inbound triples.

<!-- AUDIT-CLAIMS
- graph_state:
    uri: gemi:a52466
    nextPlannedStep: planPromote
- graph_state:
    uri: gemi:a52494
    nextPlannedStep: planPromote
- graph_triple_absent:
    subject: gemi:a55426
    predicate: gem:referencesPolicy
    object: gemi:a52466
-->
```

The audit parses the YAML and verifies each claim against the graph. **Failed claim → RED finding** (handoff statement contradicts graph). Passed claims are silent. Malformed YAML → YELLOW. Missing PyYAML → single YELLOW once (annotations still run).

Four claim types in v0.2:

| Type | Required fields | Optional fields | Verifies |
| :--- | :--- | :--- | :--- |
| `graph_state` | `uri` | `type`, `nextPlannedStep`, `isInEffect` | URI exists; each named field matches actual graph value |
| `graph_triple_present` | `subject`, `predicate`, `object` | — | Triple is in the graph |
| `graph_triple_absent` | `subject`, `predicate`, `object` | — | Triple is NOT in the graph |
| `predicate_count` | `predicate`, `expected`, and at least one of `subject`/`object` | the other of subject/object | Count of matching triples equals `expected` (integer) |

Subject/predicate/object values may use the prefixes `gemi:` (instances) or `gem:` (schema). Boolean values for `isInEffect` are case-insensitive. PyYAML is required: `pip install pyyaml --break-system-packages`.

**When to use which track.** Annotations are the safety net — they always run and surface state for every §4 item that mentions any identifier. Structured claims are assertion-strength — the handoff author records the explicit assumption ("these five are planPromote stubs") so that if the assumption goes stale between sessions, the next bootstrap halts on RED. The handoff drafter at session close is expected to add claim blocks to §4 items where the work plan depends on a specific graph state; items whose plan is state-independent (e.g., "extract NCD 240.4.1") need annotations only.

**Emitter contract: the emitter owns the emitted bytes (Tom, S157; extended S158).** Every string an emitter places into a `.ttl` literal is escaped **by the emitter**, at the point of emission, by one function. Authors of concept descriptions, rule strings, workflow notes and stub prose write **plain text** — a quotation mark is typed as `"`, and nothing in the authoring layer knows about backslashes. Hand-escaping literals in a generator's Python source is this project's most reliably repeated authoring error: S157 hit it three times in one session (`publicationNumber`, a post-Generate note, a policy description), each caught by the rdflib re-parse, each costing a cycle. **Its dangerous form is silent.** *Under*-escaping ends the literal early and fails to parse, which is loud. ***Over*-escaping parses.** `\\"` in the source is an escaped backslash followed by an escaped quote, so the literal's **value** carries a stray backslash — `\"attending physician\"` where the author meant `"attending physician"` — and rdflib round-trips it, SHACL conforms, the count is right, the predicate is right, and only a human reading the rendered value ever notices. S157 found three such literals in the corpus (`credentialAttendingPhysician` and `credentialDoctorOfMedicineOrOsteopathy` from **S41**; `conceptSevereCardiacCondition` from **S155** — two sessions old, so this is a live authoring mode, not a legacy artifact). The `literal_escape_artifact` audit check (S157) is the guard for hand-written blocks; this contract is the fix that makes the guard rarely fire. (Rule established 2026-07-17, Session 157.)

**The contract is not about escaping — it is about the bytes (S158).** An emitter owns **line endings** the same way it owns escapes. S158's generator joined each block's lines with `\n` and each section's blocks with `\r\n`, and put **223 lone-LF endings into a `.ttl` file that had zero**. It parsed. rdflib round-tripped it. The set-diff was clean and the derived predicate histogram was perfect — the same signature as the wrong-predicate emission and the over-escaped literal, and for the same reason: the author held a property of the output that the emitter should have held. The fix has the shape of the escaping fix — normalise the **whole emitted region** in one place (`'\n'.join(out).replace('\n', '\r\n')`), behind an assertion that no `\r` is authored above that line — so CRLF, like escaping, becomes a property an author *cannot state*. **The general rule is worth more than either instance: a contract that centralises one property of the emitted bytes invites the next author to assume it centralised the rest.** Everything `gem_turtle_style_guide.md` §Formatting Rules requires of a `.ttl` file belongs to the emitter — CRLF, no tabs, 4-space continuation indent, escaped literals, `.\r\n` termination — and an author writing plain text should not be able to get any of them wrong. **Unlike over-escaping, this one already had a blocking guard:** the `formatting` check fires **RED** and offers no autofix on any lone-LF in a TTL file (self-test **V15**), so the defect cannot reach the corpus. That is what the contract is for here — not to stop the defect reaching the corpus, but to stop it reaching the audit. (Extended 2026-07-17, Session 158; the instance is recorded in `gem_rule_categories.md` ### NCD 280.16.)

Before reading the policy or writing anything:

1. Read the three companion files (`worklist_schema.md`, `gem_reference.md`, `gem_turtle_style_guide.md`). This SKILL.md is already in context — the skill loads in full when it triggers, so re-reading it is wasted work (S260).
2. Read `GEM_ontology.ttl` to confirm current schema terms and conventions. If `GEM_policy_instances.ttl` already exists, read it to see which policies and codes are already present. **Before producing the Plan manifest, enumerate the promoted concept-group classes already in the schema** (e.g., `gem:QualificationGroup`, and any others added since the first checkpoint). A concept group that has already been promoted to a class must be modeled as minted individuals in the manifest — it must NOT be re-logged as a deferred proposal. Re-logging an already-promoted group is a regression. (Failure mode added 2026-05-28: NCD 240.2's Plan turn initially mislogged the already-promoted Qualification Groups framework as a deferred proposal.)
3. Read `policy_worklist.json` if it exists — the policy being processed may already be a `pending` entry.
4. Confirm the **complete** policy text is available. CMS MCD pages have heavy navigation chrome; the policy content is the substantive sections. If any section is license-gated, do not proceed — see "The Gate Hard-Stop Rule." Prefer a user-supplied PDF as the source document where one is available; PDFs render the coding sections that the web view often gates. **Prefer text-layer PDFs over rasterized ones.** A "Microsoft Print to PDF" or similar virtual-printer rendering captures each page as an image only, forcing OCR — and OCR introduces systematic character errors (`I↔1`, `0↔O`, `j↔J`, `b↔5`, `T8↔18`) that cost extraction accuracy at scale and silently mislabel a handful of codes. Diagnose by running `pdffonts` on the PDF — an empty font table is the rasterization signature. Where only a rasterized PDF is at hand, request a text-layer alternative before starting: Chrome's built-in **Save as PDF** print destination (Skia/PDF producer), or browser **Save Page As → Webpage, HTML only**, or **Save Page As → Webpage, Single File** (MHTML) all preserve the text layer. OCR of a rasterized PDF is the last resort. **PDF-authoritative for content, not just gating:** the MCD web view injects CMS-wide boilerplate the canonical PDF does not carry — most notably the "Reasons for Denial" disclaimer that appears identically across many NCD pages — so text present *only* in the web view is non-canonical and is not extracted (precedent: NCD 20.8.1, S137; see `manifest_format.md` §Reprocessing Manifests, the `metadata.source_pdf` rule).
5. **Confirm every version of the policy is available, not only the version in effect (Tom, S192).** Where the MCD lists prior versions, request all of them before extraction begins. Two things depend on it: the cross-version retention walk (below), and the policy's dates, which anchor to Version 1 (below). A single-version reading cannot supply either. Where the source genuinely publishes only one version — a policy with no Other Versions table — that is the complete set and V1 is the version in hand. Precedents: NCD 240.1 (S151, three renditions), NCD 110.18 (S186, both), NCD 220.6.20 (S191, both).
6. Assess document size and plan passes (below).

## Document Size Assessment and Reading Protocol

Most individual NCD/LCD/Article documents are small (a few thousand words) and read in a single pass. Use a word count to confirm.

| Word Count | Approach |
|------------|----------|
| Under 8,000 | Single message, two passes (sequential read, then category audit). |
| 8,000–20,000 | Single message; if context pressure builds, checkpoint. |
| Over 20,000 | Multi-message reading-notes protocol; write findings to a `reading_notes.json` on disk as you read, checkpoint at section boundaries, and present the plan only after all sections are read. State the plan and confirm with the user before beginning. |

**Close reading is mandatory.** Read every section, including the Article Text prose, the coding tables, the revision history, and the associated-documents lists. Do not rely on keyword search as the primary method — codes appear in running prose ("payment for stationary equipment (E0424, E0439, E1390, E1391)") that a code-regex would catch but whose *polarity and meaning* only close reading recovers.

**If reading is incomplete:** the response depends on the cause. For a *gated* section, follow the Gate Hard-Stop Rule — stop and request a complete PDF. For context pressure or a fetch failure on a non-gated document, say so explicitly, save progress, and ask the user how to continue. Never present a partial reading as complete.

### Scope discipline for the first policies

Per project agreement, an **initial scope discipline** modeled only policy metadata, codes, modifiers, credentials, policy-to-policy references, and clinical concepts; everything else was **logged as a deferred proposal** in the worklist. Subsequent sessions have promoted additional categories — most recently evaluator criteria as `gem:ruleDescription` strings on the policy (Session 48), pending future atomization. See the Extraction Taxonomy table above for the current modeled set. Remaining deferred proposals are revisited at each 20-policy checkpoint per the re-trigger rules below.

**Anti-curation signal:** within an in-scope category, do not filter by perceived importance. Every ICD-10 code, every HCPCS code, every modifier, every clinical concept the policy references is extracted. "Major"/"key"/"notable" are not extraction criteria. (Clinical concepts are bounded by the clinical-vs-administrative test in §Clinical Concepts, not by perceived importance.)

### The claim-readability test

When deciding whether a deferred-proposal group should be promoted into the modeled graph — or, during extraction, whether a piece of structured data is in scope at all — apply the **claim-readability test**.

The project's chief objective is to read a Medicare claim (its ICD codes, HCPCS codes, and the clinical concepts in the provider notes) and determine **which policies are relevant** to evaluating that claim — *not* to perform the evaluation itself. The test follows directly:

> **Does this structured data help match a claim to a policy?** Something is worth modeling **as claim-matchable data** only if a real claim would carry an input the matcher could match against. Numeric thresholds, study-design standards, documentation rules, timing rules, payment/bundling rules, and benefit-status determinations are *evaluation* criteria — a claim does not carry them, so they are not claim-matchable. Named clinical entities that a provider note could mention ARE claim-readable and are modeled (as flat `gem:ClinicalConcept` individuals).

**The matching layer and the rule-documentation layer coexist.** The claim-readability test gates what becomes *matchable data*; it does not gate what becomes *documentation*. Evaluation criteria that fail the test (eligibility, frequency, setting, risk-factor, documentation rules) are captured as `gem:ruleDescription` strings on the policy — they are not claim-matchable, but they are not out of scope. The matching layer drives policy identification; the documentation layer is consumed by the downstream evaluator after matching. Both coexist on the same policy individual without conflict. (Two-layer framing added 2026-06-10, Session 48.)

This test is the standing prior for every deferred-vs-model decision. It does not override the user/SME: the user still decides each promotion at the checkpoint. But a group that fails the test (it is an evaluation criterion, not a claim input) is logged and left deferred by default; a group that passes (it names entities a claim could carry) is a promotion candidate. A measurement *concept* (AHI, RDI, arterial blood gas study) is claim-readable and is modeled; the numeric *threshold* applied to that measurement is an evaluation criterion and is not.

**Deferred evaluator-criterion proposals — re-trigger conditions.** When a recurring concept group fails the claim-readability test, the right disposition at a 20-policy checkpoint is `resolved` with a forward-looking rationale, not `rejected`. The data is in-scope as content but not load-bearing for matching; schema promotion is deferred. Two well-defined re-trigger conditions move the proposal back into scope: (a) the evaluation team requests structured evaluator criteria for downstream consumption, or (b) a comprehensive policy-reprocessing pass makes uniform schema additions cheap. Until either condition fires, the underlying data is captured implicitly — via `gem:ClinicalConcept` individuals (named measurements, qualifying conditions), via policy `gem:description` text (threshold values, timing rules, bundling language), and via `gem:requiresProviderCredential` links where the evaluator-criterion framework anchors on a credentialed actor (e.g., the Final Rule 1713 F2F requirement implied by `credentialTreatingPractitioner`). (Rule established 2026-06-05, Session 40, after Frame X confirmation; applied across `deferred_proposals` #0, #6, #15, #16, #27, #34.)

**Re-trigger condition (a) fired in Session 48.** Tom's directive to begin documenting evaluator criteria — eligibility, frequency, setting, risk-factor, documentation, and similar rules — triggered schema promotion via `gem:ruleDescription`, a string-typed datatype property capturing each rule as the policy expresses it. Existing `resolved` entries in the evaluator-criterion family are not bulk-flipped to `approved`; each is revisited as relevant rules surface in active extractions, to preserve per-entry nuance. Future schema work will decompose `gem:ruleDescription` strings into atomic component properties as the right structure becomes clear from accumulated data.

**Candidate-category register.** Pending that future schema work, candidate categories are accumulated in `gem_rule_categories.md` — a working register, not a schema artifact. Each new policy's rules are categorized at Plan turn against two axes (domain applicability + rule type); the register grows incrementally. When a final schema is settled, the register's contents drive a one-time uniform graph update; until then, `gem:ruleDescription` strings remain unstructured by design. (Register established 2026-06-11, Session 48.)

### The source-fidelity principle

The graph asserts what the source asserts, at the structural level the source asserts it, with provenance. It does not synthesize aggregate claims the source does not itself make.

The principle is operational: when deciding whether to write a triple, ask whether the policy makes that exact claim somewhere on the page. If yes, write it. If the triple would be an aggregate or projection of multiple per-Group claims the source kept anchored, write the anchored claims at their proper level (the Group) instead, and let downstream queries traverse to recover the aggregate.

The principle's first concrete consequence is the **HCPCS / ICD asymmetry in Group-structured policies**. CMS Articles treat HCPCS codes and ICD-10 codes at different structural levels: HCPCS items are the policy's subject (named at the policy/Paragraph junction — in "For HCPCS codes X, Y, Z:" anchors, in the universally-denied list of the "DO NOT Support" section, and frequently in Article Text prose discussing specific codes), while ICD-10 codes are conditioning constraints (named only inside Group Codes lists, nested within Groups). Faithful extraction reflects that asymmetry: policy-level `gem:coversProcedure` and `gem:excludesProcedure` triples are written for HCPCS codes the policy names at policy level, and per-Group `gem:exclusivelyCoversCondition` triples on `gem:PolicyGroup` instances are written for ICDs the policy lists only inside Groups — but no policy-level `gem:coversCondition` triples are written for those Group-nested ICDs, because the source never asserts the un-anchored claim. A query for "does this policy reference ICD X anywhere?" pays the price of a 2-hop traversal through `gem:hasPolicyGroup`; the alternative — materializing a flat policy-level claim — would project away the per-anchor specificity that is the source's actual content. (Worked example: A52466 references J44.9 in eight Groups but at no policy-level point in the document; see `gem_reference.md` §2j.)

The principle generalizes beyond anchored coding scopes: when in doubt about whether to materialize a derived or aggregate triple, choose the more faithful representation even when it costs query convenience. Convenience is recoverable via SPARQL; lost specificity is not.

## Rule Patterns and the δ-Prefix Scaffold

Each `gem:ruleDescription` triple captures one evaluator criterion from the policy as a self-contained string. Three **Patterns** describe how a rule is sized and shaped; an orthogonal **δ-prefix scaffold** can be added when the source's structural scope needs to be preserved in the rule text.

**Source misspellings: corrected in the concept, verbatim in the rule (Tom, S152).** When the source misspells a word, the `gem:ruleDescription` carries the source's spelling **verbatim, always** — that is source-fidelity and it is not negotiable. The minted `gem:ClinicalConcept` (or credential, or other named individual) carries the **corrected** spelling in **both** its `gem:prefLabel` and its URI, with a source-fidelity note in its `gem:description` recording what the source wrote. The reason for the split: the rule string is the source's prose assertion, while the concept is the catalog entry a downstream matcher and a human reviewer both search — a misspelled prefLabel is a lookup failure, not a preserved fact, and the fact is preserved in the rule and the note anyway. S152 worked examples: NCD 270.1's V3 writes *"100% epitheliliazed wound bed"* and V2 writes *"epithelialzed"* — two different misspellings of the same word — so `ncd270.1_r9` carries V3's verbatim and `gemi:conceptEpithelializedWoundBed` carries the correction; NCD 240.1's R3 keeps *"High Resolution Computer Tomography"* while `gemi:conceptHighResolutionComputedTomography` carries *"computed"* in its prefLabel and URI. The ruling is general and supersedes the S151 reading of the S139 precedent, under which the prefLabel held the verbatim and only the URI was normalized. It closes the S139 `autonomic dysflexia` carry-forward: `gemi:conceptAutonomicDysreflexia` already matched it. **The rule is unconditional and has no exception clause — read it that way (Tom, S157).** It does not ask whether the source's error is a *genuine* misspelling as against a typesetting or OCR artifact, and that distinction must not be imported: it cuts the wrong way. If the source's form is an artifact, then the source's *term* is the corrected form, so the concept must carry the correction all the more — an artifact is more clearly not-what-the-source-meant than a misspelling, not less. S157 worked example and cautionary tale: NCD 280.14 prints *"HbAlc"* (lowercase L for the numeral one in the term of art HbA1c). The extraction first minted `conceptGlycosylatedHemoglobinLevelHbAlc` at the source's form, reasoning from an antecedent — *"where a genuine spelling error"* — **that appears nowhere in this rule and was invented in the write-up**. Tom corrected it in the same session: `gemi:conceptGlycosylatedHemoglobinLevelHbA1c`, prefLabel *"glycosylated hemoglobin level (HbA1c)"*, with `ncd280.14_r6` keeping *"HbAlc"* verbatim. **A misspelled or artifacted URI is an error, not a preserved fact.** **Scope of the correction: prefLabel, URI, and any prose that summarizes rather than quotes.** A policy's `gem:description` is Claude's summary, not a quotation, so it carries the term; a `Governing text:` quotation inside any description is verbatim and keeps the source's form, as does every `gem:ruleDescription`. Record the variant in the individual's `gem:workflowDescription`.

### What belongs as a rule

A `gem:ruleDescription` triple is for an evaluator criterion — something a claim is tested against. A sentence that does not guide the execution of any rule is not itself a rule.

The selection test: does the candidate rule stand on its own (its own predicates, its own conditions, its own definition) and does it actually drive an evaluator decision? If yes — capture it. If the candidate's only contribution is context or motivation for a separately-captured testable rule, it is not a rule itself.

Four corollaries recur in extraction. The first two clarify what to **drop**:

1. **Statutory framing.** "Section X of the Y Act authorizes / mandates / provides for…" is a statutory anchor. It is not a rule unless the statute's text or numeric reference is needed to execute a downstream rule (e.g., "X is covered when Y is met as defined in §1862(a)(1)(A) of the Act" — here the §1862 reference is inside the testable rule). When a statute is named only to explain why the policy exists, capture the reference in the policy's `gem:description`; do not create a standalone rule.

2. **Definitions whose content is already preserved on a named entity.** A definitional sentence ("X means …") is captured as the `gem:description` of the corresponding named individual — a `gem:ClinicalConcept` for clinical concepts, a `gem:ProviderCredential` for provider credentials, an external **`hcpcs:` (or `icd10:`/`cpt:`) code IRI** whose official descriptor (`skos:prefLabel` in the always-co-resident HCPCS/ICD/CPT reference dataset) defines the item, and parallel logic for other entity types as they arise. If the rule that names the entity does not require the definition to execute, the definitional sentence is not a separate rule. **For an HCPCS code-descriptor sentence ("HCPCS code X is/describes …", "An X (Ennnn) delivers …"), the code's identity is carried by the co-resident `hcpcs:` descriptor, so a *pure* device/item definition is dropped; only the rule-bearing increment beyond the official descriptor — a coding directive, a unit-of-service rule, a prohibition — is captured, as a contiguous source passage carrying that increment. Two equivalent examples: a coverage rule that says "Screening X is covered when Y" executes by HCPCS code matching, not by re-reading the "X means a procedure that …" definition; a coverage rule that says "ordered by the primary care physician" executes by matching the claim's provider to the credential individual, not by re-reading the §1833 enumeration. In each case the definitional content already lives on the named entity's description.

The next two clarify what to **keep**, even when #1 or #2 might naively suggest dropping:

3. **Verbatim-capture posture.** When the source restates the same rule in multiple forms with material differences (different wording, different qualifications, different framing), capture all forms verbatim as separate rules rather than picking a "best" version, paraphrasing, or merging. The same posture applies to adjacent contextual content that supplements the rule without competing with it — soft-expectation framing, in-rule statutory citations, sentence companions that are part of the source's prose statement of the rule. The principle is *don't drop content that is in the rule or immediately adjacent*, even when corollaries #1 or #2 might be read to suggest dropping. The structured triples elsewhere encode the enforceable semantic; the rule string captures the source's prose assertion; both serve different downstream consumers.

4. **Verbatim-cross-reference posture.** When source prose carries a cross-reference (`"...as defined in section X"`, `"...not listed under section Y"`, `"...per the related LCD"`), capture the verbatim reference as written in the rule string. Do not inline the referenced section's content into the rule, do not substitute a paraphrased version of what the reference points at, and do not drop the rule because the structured triples elsewhere already encode the same meaning. The rule string's job is to capture the source's prose assertion; the cross-reference *is* the source's prose. (Standalone navigational sentences — *"Refer to CMS Publication 100-04..."* — are a separate question governed by the broader verbatim-capture posture in #3. A standalone **policy-scope non-alteration / non-withdrawal clause** ("this policy does not alter/withdraw coverage under Z") *is* rule-bearing — captured as a single `coverage-scope` rule because it asserts a coverage-effect boundary — whereas a bare navigational scope-boundary pointer ("X for other uses is addressed in the Z LCD") and a bare definitional pointer ("X is defined in 42 CFR §Y") are both dropped; see gem_rule_categories.md § "Scope-boundary sentences: capture vs. drop".)

### Cross-version retention (multi-version policies)

When the user supplies more than one version of a policy, the rule set is not simply the current version's text. **The cross-version retention rule (Tom, S151):** *if an earlier version states a rule, concept, healthcare setting or beneficiary group, and a later version does not, and no revision history in any version reports the change, then nothing changed — the factor stands until a specific statement removes it.* A version that merely **fails to report** a change has not made one. Silence is not deletion.

**Sequence matters, and it is tested V1 → intervening → newest, not V1 → newest.** If V2 removes something, V3 cannot add it back — the removal already happened and V3's silence inherits the removed state. If V2 is silent about a V1 factor, V3 inherits V1 unchanged. Walk the chain in order; each transition is its own test.

**What counts as "reporting the change" is a specific statement, in a revision history, about the factor in question.** A revision-history entry that reports *some other* change does not license reading a silent drop as intentional. Contrast the two S151 outcomes on NCD 240.1: TN 44's entry reports only *"Modified requirements for facilities eligible to perform lung volume reduction surgery"*, so V3's silent drop of V2's NETT-participant coverage leg is **not** a removal and the leg is retained (`ncd240.1_r10`); but that same entry **does** report the facility-criteria replacement, so V2's NHLBI-threshold facility criteria **are** removed and are not retained.

**A restatement is not an absence.** When a later version states the rule in its own (often condensed) words, that version's text governs — B2' below. Test the parts the restatement *dropped* individually; each is its own silent-absence question.

**Retained rules are ordinary rules (B2', Tom, S151).** A `gem:PolicyRule` **declares itself by its existence**. When a later version revises it, the rule's text changes; when a later version deletes it, the individual is deleted. So a retained rule carries no version stamp, no provenance annotation, and no marker distinguishing it from a current-version rule — it is a `gem:PolicyRule` with `dc:source` to the policy, like any other. Its text is **the last version that spoke to it**. Do not merge text across versions into one `gem:ruleDescription`: that is exactly the merge source-fidelity corollary #3 forbids. If V1 and V2 both speak to the same ground in different words, that is two rules, and the downstream process resolves the difference.

**Consequence to state at the end-of-policy presentation.** The retention decision is not derivable from the graph — a reader cannot tell a retained V1 rule from a current-version rule without the register. That is a known, accepted gap under the current design; it is logged as `deferred_proposals[98]` (multi-version management). Write the narrative into `gem_rule_categories.md` and into `gem:workflowDescription` on the policy, and name the count delta against the Plan-turn manifest if the rule changed it.

**Concepts, settings and beneficiary groups are in scope too, not just rules.** S151 worked example: NCD 240.1's V1 and V2 both name COPD; V3 says only "severe emphysema"; no revision history reports the narrowing, so `conceptCOPD` stays linked.

**But the concept clause governs *silent* drops only — a concept named solely inside a reported-removed rule goes with the rule (Tom, S152).** When a revision history *reports* the removal of a rule, the rule goes; so does any concept, setting or beneficiary group that appears nowhere in the policy except inside it. Without this, every reported removal would leave its vocabulary stranded and the policy would accrete concepts its current text contradicts. S152 worked example: NCD 270.1's V2 states *"Any form of electromagnetic therapy for the treatment of chronic wounds will not be covered"*, and TN 7's entry reports exactly that change, so the rule is not retained — and because the phrase *"chronic wounds"* appears in no other rule of any version (V3 speaks of *chronic ulcers*), `conceptChronicWound` is not minted either. The test is scope, not sentiment: if the concept is named anywhere else in any surviving version's text, it stays; if the removed rule was its only home, it goes.

**A silently-dropped factor that was never a rule is retained as concepts, not as rules (Tom, S152).** Retention retains rules, concepts, settings and beneficiary groups — it does not *promote* prose into a rule it never was. When an earlier version's silently-dropped passage fails the "what belongs as a rule" test (background description, motivation, or a definition whose content belongs on a named entity under corollary #2), retain its **concepts** and mint **no** `gem:PolicyRule`. S152 worked example: NCD 270.1's V1 enumerates the ES modality taxonomy (direct current, alternating current, pulsed current, pulsed electromagnetic induction, spinal cord stimulation; TENS as an AC example; PEMI including PEMF and PEE; generators and coils rather than leads and surface electrodes) in its Item/Service Description. V2 drops all of it and TN 161's entry reports only the coverage changes — a clean silent drop — but the taxonomy drives no evaluator decision, so 16 concepts entered the graph and no rule did. The pull to mint one is real and should be resisted: minting a rule the source never wrote as one, to preserve content the concepts already carry, is retention manufacturing evidence. Contrast NCD 240.1's `r11`, which *was* retained as a rule — its itemization sits **inside** a coverage rule and tells the evaluator what is covered.

**Retention can also return nothing, and that is a result.** NCD 270.1 (S152) is the corpus's second multi-version policy and retained no rule at all: one silent drop was a restatement-with-changed-outcome (V2's *"all other uses … are noncovered"* against V3 §C's MAC discretion — the same ground, a different disposition, so specifically changed), the other was reported. Write the analysis into the register either way; "nothing retained" is a finding about the versions, not a step skipped.

(Rule established 2026-07-16, Session 151, at NCD 240.1 — the corpus's first multi-version rule set.)

### Policy dates anchor to Version 1

**`gem:policyEffectiveDate` and `gem:policyImplementationDate` both take Version 1's values (Tom, S191 and S192).** The properties are named for the policy and sit on a policy subject, so they must state policy-level facts. A date taken from whichever revision happens to be current is a version fact wearing a policy name, and for every individual with a version greater than 1 it reads as a false statement about the policy. V1's effective date is the open end of the union of the versions' intervals — the date the policy began.

**Both predicates move together, or neither.** They carry the identical `llmCardinalityNote` ("One per policy version") and the identical subject/name mismatch. Anchoring one to V1 and leaving the other on the current version would put two dates on one individual describing two different versions.

**Do not manufacture a date the source does not publish (Tom, S192).** Where a document carries no implementation date — LCDs and Articles do not publish the field at all — the individual carries no `gem:policyImplementationDate`. Absence is the accurate record, and it is not a gap to be filled. Record the absence; do not infer a value from the effective date or from a sibling version.

**Where V1 publishes no implementation date, drop the triple (Tom, S192).** Older NCDs routinely leave the MCD's Implementation Date field empty on V1 — 15 of the 39 NCDs corrected at S192 did. The individual then carries no `gem:policyImplementationDate` at all. Keeping the current version's value would be the mixed-anchor state this rule exists to end, and inventing one is forbidden outright. Version-specific implementation dates are a separate future capture, not a reason to hold a wrong value now.

**Where Tracking Information declines to post V1's effective date, read the Other Versions table instead.** Longstanding NCDs print *"This is a longstanding national coverage determination. The effective date of this version has not been posted"* in the Tracking block, while the **Other Versions** table on the same page still gives V1's range, opening at 01/01/1966. Take `gem:policyEffectiveDate "1966-01-01"^^xsd:date` from that column. This is a published value in another field, not a manufactured one, and it preserves the every-processed-policy-has-an-effective-date invariant. No implementation date accompanies it. Precedents: NCD 30.1, 110.3, 240.3, 270.4, 270.5, 280.2, 280.7 (all V1), and at S192 NCD 30.3, 160.8 and 280.3.

**Only a date that no field of the source publishes is genuinely unavailable.** Exhaust the Tracking block and the Other Versions table before concluding one is missing; then say so in the register and leave the recorded value alone rather than guessing. An unrecoverable V1 date is a research outcome, not a licence to substitute the current version's.

**Migration in progress — read this before "correcting" an apparent contradiction.** The already-extracted corpus predates this rule and most of it is still anchored to the current version; `deferred_proposals[107]` tracks the correction, and `gem_reference.md`'s definitions of the two properties still describe the old reading **deliberately**. Under `[107]`'s own constraint the definition must not land ahead of its values (the S45 failure mode: a rule stated, values unmigrated, and no way to tell compliant from non-compliant). The `gem_reference.md` wording is therefore corrected at the end of the migration, not now. Until then the disagreement between this section and `gem_reference.md` is expected and must not be resolved in either direction by a session that encounters it.

**New extractions comply by construction** — the versions are in hand under Pre-Extraction Requirement 5, so V1's dates are read directly and no correction is ever owed. Precedents: NCD 110.18 (S186 B9), NCD 220.6.20 (S191 B2), the first two policies compliant by construction. Date-anchoring is a settled rule applied silently at extraction — it is no longer surfaced as a per-policy borderline (S237).

### Rule decomposition framework

The corollaries above define *what counts as a rule*. The Patterns below define *how each rule is shaped as a string*. Between them sits a third question: when a single source passage holds multiple IF/THEN clauses, how many rules should it produce? Three coupled principles answer it as a pipeline — count, classify, decompose.

**1. The IF/THEN heuristic for granularity.** Count the IF/THEN statements a downstream evaluator would generate from the source paragraph. The natural rule count for `gem:ruleDescription` capture equals that count. Internal `OR` disjunctions inside a single Boolean expression do not fork further — they remain inside one rule.

(Principle articulated 2026-06-17, Session 64, by Tom: *"If I were writing rules in Python, I would count up how many IF x THEN (covers or excludes) statements would be produced by a sentence."*)

**2. Parallel vs. sequential decisions.** Once the IF/THEN heuristic has counted N rules from a passage, distinguish two shapes:

- **Parallel decisions** — N IF/THENs that are alternative paths to a similar decision or shared outcome. Captured as N rules with framing duplication where needed. Worked example: NCD 240.2 §B Group I sleep bullet (B4 / R8+R9 — Statement A + Statement B as alternative qualifying paths).
- **Sequential decisions** — N IF/THENs that answer logically distinct questions chained in order. Captured as N rules, each standing alone. Worked example: NCD 240.2 §D MAC discretion (B6 / R19+R20+R21 — initial discretion, duration, renewal).

The IF/THEN heuristic counts the rules; the parallel-vs-sequential test shapes them.

(Principle articulated 2026-06-17, Session 64, by Tom: *"It seems like it would be important to recognize sequential decisions from parallel decisions and use that to guide how we capture rule descriptions."*)

**3. Shared-X-per-case-Y variants.** With N rules counted (per #1) and their shape classified (per #2), characterize the relationship across rules by identifying what is *shared* and what is *per-case*. Four variants observed empirically across NCD 240.2's S64 reprocessing pass:

| Variant | Shared element | Per-case element | NCD 240.2 anchor |
|:---|:---|:---|:---|
| Shared framing + per-case body | Rule statement + general definition | Patient-class-specific sub-case | B2 / R5+R6 (§B time-of-need: inpatient vs. outpatient) |
| Shared outcome + per-case qualifying tree | Coverage decision + restrictions | Distinct qualifying conditions | B4 / R8+R9 (§B Group I sleep bullet: Statement A vs. Statement B) |
| Per-case independent rules | (none) | Distinct sequential decisions | B6 / R19+R20+R21 (§D MAC discretion: initial / duration / renewal) |
| Shared qualifying tree + per-case outcome shape | Qualifying conditions (one IF) | Outcome shape labels only | B8 / R22 (§D portable-oxygen: "either (1) by itself, or, (2) to use in addition to a stationary oxygen system") |

Variants 1–3 each produce N rules per the source's natural decomposition. Variant 4 is a boundary case: the per-case element is *only outcome shape*, not structural divergence in the qualifying tree, which under the IF/THEN heuristic (#1) yields one IF and thus one rule. The source's *"either (1) … or (2) …"* enumeration stays inside the verbatim string of that single rule.

Applied at NCD 240.2's S64 reprocessing pass: the four rule-decomposition borderlines (B2, B4, B6, B8) each anchor on specific rules in the 22-rule policy. `gem_rule_categories.md`'s NCD 240.2 row carries the B-ID tag on each anchor rule (R5+R6, R8+R9, R19+R20+R21, R22), and the §Notes paragraph for each borderline explains the per-rule reasoning.

### The three Patterns

**Pattern 1 — single-sentence, no heading repetition.** One discrete sentence from the source, captured verbatim. Used when the sentence is self-contained — its meaning doesn't depend on a heading or surrounding context. Most rules fall into this Pattern.

Example (NCD 230.18 R1): *"Effective January 1, 2002, sacral nerve stimulation is covered for the treatment of urinary urge incontinence, urgency-frequency syndrome, and urinary retention."*

**Pattern 2 — heading-repeated, natural-prose prefix.** A single-sentence rule where the source's heading is repeated as a natural-language prefix in front of each rule that belongs to it, separated by a colon. Used when a flat list of bullets/sentences appears under a single labeled heading and each item depends on the heading's context to be interpretable as a rule.

Example (NCD 230.18 R3): *"Limitations (apply to all three indications): Patient must be refractory to conventional therapy (documented behavioral, pharmacologic and/or surgical corrective therapy) and be an appropriate surgical candidate such that implantation with anesthesia can occur."*

**Pattern 3 — multi-sentence (paragraph-level).** Two or more sentences captured as a single cohesive rule because they form a single logical unit (a definition, a procedure description, a multi-sentence eligibility criterion). The sentences are joined by their original whitespace; no internal scaffold is added.

Example (NCD 230.18 R2): *"Sacral nerve stimulation involves both a temporary test stimulation to determine if an implantable stimulator would be effective and a permanent implantation in appropriate candidates. Both the test and the permanent implantation are covered."*

### The δ-prefix scaffold (orthogonal to Pattern)

When a source has letter-labeled sub-items (`a.`, `b.`, …), multi-level nesting (`BR 04.1.3.1`), or in-rule cross-references to other items in the same group ("With respect to item a, …"), the natural-prose Pattern 2 is insufficient — the scope information needs to be preserved explicitly enough to support structural queries. The **δ-prefix scaffold** is a bracketed meta-annotation prepended to the verbatim text:

```
[<label> <parent_id> scope: <parent scope keyword>] <verbatim text>
```

Where `<label>` is `Section` for Manual-section numbering, `BR` for Business Rule numbering (TN 2476 precedent), or a phrase identifying the scope group; `<parent_id>` is the numeric/letter identifier of the parent; `<parent scope keyword>` is a brief description of what the parent scopes.

Multi-level nesting chains the prefix with semicolons (e.g., `[BR 04.1 scope: ...; BR 04.1.3 scope: ...] <verbatim>`).

Example (NCD 160.7 R10): *"[Section B.2 scope: conditions for coverage of dorsal column or depth brain stimulator implantation] a. The implantation of the stimulator is used only as a late resort (if not a last resort) for patients with chronic intractable pain;"*

The δ-prefix is **orthogonal** to Pattern: a rule can be Pattern 1 + δ-prefix (most common), Pattern 3 + δ-prefix (rare), or used without Pattern 2 (the natural-prose heading and bracketed scaffold serve overlapping purposes; pick one).

### Selection rule

| Source shape | Pattern | Scaffold |
|:---|:---|:---|
| Verbatim is self-contained (subject + verb + condition in one sentence) | 1 | none |
| Multi-sentence cohesive paragraph | 3 | none |
| Flat bullet/numbered list under one heading, no sub-numbering | 1 or 3 (by granularity) | Pattern 2 heading-repeated |
| Letter-labeled sub-items, multi-level nesting, or in-rule cross-references | 1 or 3 (by granularity) | δ-prefix |
| Deeply hierarchical (3+ levels of nesting like TN 2476's BR 04.1.3.1) | 1 throughout | δ-prefix with semicolon-chained levels |

### Examples-folded vs δ-atomized

When an enumerated list in coverage prose is explicitly **non-exhaustive / illustrative** ("might include", "such as", "e.g."), fold it verbatim into the parent rule and keep members queryable via concept links — do **not** atomize into δ-scoped sub-rules (δ implies a closed gate). Contrast true **"only when: (1)…(2)…" gates** (NCD 160.13, NCD 160.18 CED template), which do atomize. (Established S115, NCD 160.8 R4 — "such other procedures might include…" folded, not split.)

### Line-wrap de-hyphenation (verbatim-string normalization)

When the source PDF breaks a hyphenated word across a line — a line ends with an alphanumeric character plus a hyphen and the next line continues the same word — rejoin the fragments **without inserting a space**, giving the unbroken token the source intends (`6-month`, `2-week`, `CAG-00465N` — never `6- month`). The line break is incidental `pdftotext` layout; the hyphen belongs to the word, so the joined form is the faithful verbatim and the inserted-space form is an extraction artifact.

Preserve genuine spaced or suspended hyphens unchanged. A hyphen the source itself follows with a space — including the suspended-compound form `short- or long-term` — is real punctuation, not a wrap, and is captured as written. De-hyphenation fires **only** across a line break, never on an in-line `X- word`.

The one ambiguous case is a suspended hyphen broken *at* a line end (`short-` ending a line, `or` beginning the next), where a naive lowercase-continuation join would wrongly yield `short-or`. When the token after a line-end hyphen is a standalone connective (`or`, `and`, …) rather than a word-fragment continuation, verify against the rendered page image before joining.

(Rule established 2026-06-29, Session 102, after NCD 240.9's `6-month` / `2-week` line wraps. Pre-S102 captures predate it; NCD 240.2 R1 carries the un-rejoined `long- term` form and is flagged for a verbatim-review check.)

### Transitional status

The δ-prefix scaffold is **transitional**. When a future ζ schema extension is adopted (first-class `gem:Rule` individuals with `gem:parentRule` structural links), the bracketed scaffold will be migrated to graph triples and removed from the rule string. Until ζ is adopted, the δ-prefix keeps the parent context queryable as part of the literal string.

(Patterns established across Sessions 39–49; canonical definitions codified 2026-06-12, Session 50.)

## The Three Code Contexts

A code's meaning depends on **where in the document it appears**. Distinguish three contexts; treat each differently.

| Context | Example | Treatment |
|---------|---------|-----------|
| **1. Coding tables** | The "ICD-10-CM Codes that DO NOT Support Medical Necessity" table listing J96.01, J96.11, J96.21, J96.91, R09.02. | Highest confidence. The table heading gives polarity directly. Extract every code; record the heading and any group paragraph as the governing context. |
| **2. Article/policy prose** | "payment for stationary equipment (E0424, E0439, E1390, E1391)"; "Oximeters (E0445) … will be denied as non-covered." | Reliable, but polarity must be read from the sentence. A code in a coverage statement is covered; a code in a denial statement is non-covered. Record the governing sentence. |
| **3. Revision history** | "Added: ICD-10 codes J96.01, J96.11 … to Group 1"; "Removed: Q0 modifier." | **Change-log artifacts for CODES: do NOT create *code* reference triples from revision history.** (Document-reference citations in revision history — transmittals, CRs, other policies — ARE now minted; see "Revision-history references" below.) A code may optionally be noted, but the current coding tables and prose are the source of truth for what the policy references *now*. |

**Revision-history references — codes excluded, document citations now minted (S131 reversal).** Two different things appear in a Revision History and are handled differently. **(a) Codes** named only in revision history remain change-log artifacts and are NOT captured (row 3 above) — the current coding tables and prose are the source of truth for what a policy references *now*. **(b) Policy-document references** — transmittals, Change Requests, NCAs, or other NCDs/LCDs/Articles named *anywhere* in a policy, including in Revision History — ARE now minted. Per the **mint-every-referenced-policy rule** (established S131, Tom's direction): *if a policy references another policy document, mint a stub for it (`gem:nextPlannedStep gem:planPromote`) and assert the citing policy's link to it — regardless of what the referencing policy tells us about it.* The referencing policy's one-line characterization (e.g. a rescind-reason that names a *different* NCD) is not a reliable guide to relevance and is **not** used to gate the mint; the referenced document is analyzed later at its own pass, and that analysis stands on its own (it may capture the document's own outbound references to *other* policies even if it says nothing back about the referencer). This **reverses** the prior "revision-history document citations are excluded" rule. Minted stubs go directly to the graph, not the worklist. (Precedent: NCD 160.18, S131 — all 31 header/claims-processing/revision-history transmittals + 18 cited CRs minted as `planPromote` stubs.) **S147 option (b) is retired (Tom, S190 borderline B8; applied corpus-wide S191).** NCD 160.24's S147 pass read this same shape the other way — an NCD named only inside a *transmittal's* rescind-reason was held off the graph on the ground that the reference's proper home was that transmittal's own outbound link, to be asserted at its future pass — and recorded three such references (NCD 90.2, NCD 210.3, NCD 20.33) on `policy_worklist.json` instead. S190's B8 minted NCD 90.2 and NCD 110.24 on exactly that shape and Tom confirmed it, which settles the rule-text-versus-precedent conflict the S147 register left open: **the citing policy asserts the link, and a mention inside a quoted rescind-reason is still a mention by the citing policy.** The three S147 worklist entries were minted and struck at S191. **Link polarity for these references (mint-now-analyze-later).** The citing policy asserts the **agnostic** `gem:referencesPolicy` to each named document — it names it; that is all the current text supports. The stronger `gem:revisesPolicy` (transmittal → the policy it revised) is asserted **only after** the transmittal is analyzed and confirmed to have revised the citing policy; it is not inferred from a bare revision-history mention. The pairing is stated verbatim in the source ("(TN 10432)(CR12027)"), so each edge is a directly-stated fact asserted at mint. `dc:source` stays the single in-effect deliverer. **A CR named in narrative with no delivering transmittal identifiable from the citing document is minted the same way (Tom, S190 Q1; applied corpus-wide S191).** It is a `gem:ChangeRequest` stub (`planPromote`) like any other, linked from the *citing policy* by `gem:referencesChangeRequest` — the mention relationship, the `gemi:ncd160.24 → gemi:cr8109` shape — because no transmittal is available to carry `gem:transmitsChangeRequest`, and it is minted **Source-pending**: the CR sourcing convention resolves to the delivering transmittal's IRI, and no deliverer is inferred by analogy. This supersedes `worklist_schema.md`'s "mentioned but not minted" reservation for `reference_type: ChangeRequest`, which now covers only a CR whose *identifier* is not resolvable from the text. Full CR extraction awaits a CR-extraction methodology (not yet designed). (Former counter-example, now superseded: NCD 240.1's Revision-History TN 3/102/83 would today be minted as stubs.)

**Gated sections are handled by a hard stop, not by flagging.** Earlier versions of this skill flagged a gated section and continued. That is no longer correct: a gate means the document is incomplete, and extraction does not proceed from an incomplete document. See "The Gate Hard-Stop Rule" immediately below.

## The Gate Hard-Stop Rule

CMS MCD coding sections are frequently **license-gated** in the web view: instead of the codes, the section renders "Please accept the License to see the codes" or equivalent. The AMA copyright on CPT/HCPCS descriptions is the reason the gate exists.

A gate is fundamentally different from a "N/A" section. In a *complete* document, a section reading "N/A" is confirmed empty — the policy genuinely has nothing there. A *gated* section is withheld content: codes may well be present and simply hidden. Treating a gate as if it were a confirmed zero would silently tell the ontology a policy references no codes when it may reference many.

**The rule:** the moment a gate is encountered, **stop**.

1. **Stop immediately.** Do not produce a partial Plan turn. Do not extract from the readable sections and flag the gated one — the whole extraction halts.
2. **Tell the user** which section is gated and that the document is therefore incomplete.
3. **Request a complete PDF** of the policy document (NCD, LCD, or Article). A user-supplied PDF renders the coding sections the web view gates.
4. **Wait.** Do not proceed on the partial document.
5. **Restart the analysis from the beginning** once the complete PDF is supplied, so the Plan turn is built from the full text.

This applies to **every** gate, regardless of whether the gated section is within current extraction scope — a gate on an out-of-scope section (Bill Type Codes, Revenue Codes) still triggers the stop. The user may override the hard stop with an explicit instruction; absent that override, a gate always stops the work.

**Rationale for stopping even on out-of-scope gates:** the project maintains a library of complete policy PDFs so that a future scope expansion never requires re-fetching and re-reading a document. Capturing the complete PDF on first encounter, every time, serves that library.

## Polarity: Covered vs. Non-Covered

For every diagnosis and procedure/item code, determine whether the policy references it as **covered** (supports coverage / medical necessity) or **non-covered** (does not support medical necessity, denied, excluded). This is essential: a claim-relevance ontology that links a denied item with a "covers" predicate is actively misleading.

**Rules:**
1. Polarity is determined **per code**, from the table heading or prose sentence governing that specific code — never from the document overall. One document routinely contains both (E1390 covered; E0445 non-covered; the J96.x table non-covered).
2. Use **separate predicates** for the two polarities (covered vs. non-covered) for each code type — see `gem_reference.md` for the predicate names.
3. **Predicate vocabulary by polarity.** ICD-10 uses `gem:coversCondition` and `gem:excludesCondition`; HCPCS procedures/items use `gem:coversProcedure` and `gem:excludesProcedure`; healthcare settings use `gem:coversInHealthcareSetting` and `gem:excludesHealthcareSetting` (S197 — see §Healthcare Settings). These remain sub-properties of `gem:refersToICDdiagnosis` and `gem:refersToHCPCSprocedure` **in the schema**, so a query on a parent still returns references of either polarity by entailment — but the neutral parent is **not asserted directly** by new extraction (see rule 4). Modifiers have no polarity pair — `gem:refersToHCPCSmodifier` is single, polarity-neutral.
4. **Decision rule for assigning polarity — binary (two tiers), applied to each code:**
   - **Tier 1 — denial stated.** Heading, prose sentence, or table title says "not covered" / "noncovered" / "does not support medical necessity" / "denied" / "excluded" / "invalid for claim submission" / equivalent for this specific code. Use the **`excludes…`** predicate (`gem:excludesCondition` / `gem:excludesProcedure`).
   - **Tier 2 — covered or silent (the default).** Anything that is not a denial: explicit coverage ("covered" / "supports medical necessity"), an explicit disclaimer of polarity ("the appearance of a code in this section does not necessarily indicate coverage"), **or** no polarity statement at all. Use the **`covers…`** predicate (`gem:coversCondition` / `gem:coversProcedure`). Neutral is not modeled separately; a code that is not denied is taken to be covered.
   - The polarity-neutral parents (`gem:refersToICDdiagnosis`, `gem:refersToHCPCSprocedure`) are therefore **never asserted directly** in new extraction. They survive in the schema only as parents reached by entailment. (Rule established 2026-05-28, Session 19, superseding the prior three-tier scheme in which an explicit disclaimer used the neutral parent. Legacy L33797 triples asserted under the old scheme await a backfill pass and are the only remaining direct uses of the neutral parents.)
5. **Always record the governing sentence or heading** for every code in the Plan manifest, **including the tier** the polarity assignment fell under (Tier 1 denial / Tier 2 covered-or-silent). This is the evidence for the polarity assignment and lets the user verify it. A Tier-2 assignment reached by silence (not by explicit coverage) is not invisible in the manifest — it must say "polarity tier: 2 (covered/silent default)" so the user sees the inferred polarity, not just the predicate.
6. If polarity is genuinely **ambiguous** — meaning the document gives **conflicting** signals for the same code (e.g., named as covered in one section and as non-covered in another, or a single sentence both supports and denies) — do not guess and do not fall back to the covered default. Flag the code as `polarity: uncertain` in the manifest and ask the user.

**Denial-language phrasing on a coded reference triggers Tier 1 even in descriptive or structural usage.** When source text negates a procedure-code reference inside a definitional sentence — e.g., "[the item] does not include X (CODE)" or "[the equipment] is not provided with Y (CODE)" — the structural framing does not soften the polarity. The phrase asserts that the code is excluded from the scope being defined; the policy's bottom-line treatment of that code is `gem:excludesProcedure`, not `gem:coversProcedure` with a caveat. The downstream evaluator matching a claim with CODE against this policy must reach the denial outcome, and the structured-data assertion must carry that. Worked example: A52519's "Suction equipment does not include … canisters (A7000)" — the descriptive-negation phrasing places A7000 on `gem:excludesProcedure`, not on `gem:coversProcedure`. (Sub-principle established 2026-06-15, Session 60, borderline B2; codified in this skill 2026-06-16.)

**Closed-list refinement of Tier 2 (sub-property pair).** When a policy makes the covered set closed — i.e., the source declares (or its structure implies) that the listed codes are the ENTIRE set covered for the subject scope and all others are excluded — use the closed-list sub-property in place of plain covers: `gem:exclusivelyCoversCondition` instead of `gem:coversCondition`, `gem:exclusivelyCoversProcedure` instead of `gem:coversProcedure`. These are sub-properties (same polarity as Tier 2), so a query on the parent still finds them. Two source patterns trigger the closed-list refinement: (a) a "DO NOT Support Medical Necessity" section that lists no specific codes but declares the complement excluded (policy-wide pattern), or (b) a Group Paragraph that anchors a finite ICD list to a finite HCPCS list (per-Group pattern; see §Anchored Coding Scope Modeling). When neither pattern applies, plain `gem:coversCondition` / `gem:coversProcedure` is correct.

**Cross-policy polarity differences are not extraction errors.** Two policies in the same domain may legitimately mention the same code from different perspectives — one as part of its scope, one as an explicit exclusion. The graph captures both faithfully; the downstream evaluator weighs them under the project's standing rule that denial language overrides approval language. Claude does not propose to "reconcile" such differences across policies, and cross-policy polarity comparison is not part of the verification checkpoint. *Within*-policy polarity contradictions are a different matter: a single policy showing one code on both `coversProcedure` and `excludesProcedure`, or polarity that contradicts the code's own governing text, indicates a likely extraction error and should be flagged. (Rule established 2026-06-01, Session 32, prompted by the A52514-excludes / L33797-covers E0445 pattern surfaced during mock-claim relevance testing — confirmed as the expected two-perspectives pattern, not a contradiction to fix.)

**Contractor (MAC) discretion — the third disposition (`gem:delegatesCoverageTo`, S167).** Some rules make neither a national covered nor a national non-covered call: the policy hands the coverage determination to a Medicare Administrative Contractor. When a rule delegates its coverage determination to a MAC or the MAC medical staff, attach **`gem:delegatesCoverageTo`** on the `gem:PolicyRule` pointing at the delegatee `gem:ProviderCredential` — `gemi:credentialMedicareAdministrativeContractor` (delegation to the MAC as a whole) or `gemi:credentialMedicalStaff` (delegation to the MAC medical staff specifically). Presence of the predicate is the contractor-discretion marker; the object is *to whom* it is delegated. Two shapes both use it: **(A) whole-policy no-national-determination delegation** — CMS declines or removes an NCD and states determinations are made by the MACs under §1862(a)(1)(A) via the LCD process or case-by-case adjudication (NCD 200.2, 180.2, 240.2.2); and **(B) bounded delegation inside a nationally-covered frame** — a specific sub-decision handed to the MAC or its medical staff (NCD 260.1's liver-transplant malignancies; NCD 280.7's variable-height/electric bed features; NCD 280.14's other-uses infusion-pump determinations). The rule still carries its `gem:ruleType`s (typically `coverageScope`, plus `statutoryFraming` for shape A, plus `credentialedActor` for shape B) and its verbatim `gem:ruleDescription` as before; `gem:delegatesCoverageTo` adds the disposition facet on top. This facet records *to whom*; it is orthogonal to — and does **not** substitute for — the deferred `gem:CoverageDecision` disposition value `gem:mac_discretion` (`deferred_proposals[72]` Phase 2), which records *what* the disposition is and remains deferred. Do not treat a MAC-discretion rule as a non-coverage rule: the item is not denied, so it does not take `excludes…` predicates by virtue of the delegation. (Implemented 2026-07-18, Session 167, as `deferred_proposals[90]`. The **S168 complete-sweep** — a corpus scan of all 1388 `gem:PolicyRule` individuals across the 80 processed policies for discretion language lacking the predicate — added seven more, all → the whole MAC (`gemi:credentialMedicareAdministrativeContractor`): NCD 20.29 (R7, Section C removed → MACs may determine), 240.2 (R19 home-O₂ R&N for other patients, R20 initial-coverage duration at MAC discretion), 270.1 (R16, other ES/electromagnetic uses at local MAC discretion), 280.16 (R4, DME MAC seat-elevation discretion), 280.1 (R94, MAC determines home-vs-outpatient site), 50.1 (R9, A/B MACs cover-or-not SGDs). Two borderlines were excluded as *not* delegations — a generic Program-Integrity-Manual statement of LCD R&N authority and a "carrier may determine the RUL" useful-lifetime parameter. The predicate now spans 20 rules and `[90]` is `complete`.)

## Provider Credentials

A **provider credential** (`gem:ProviderCredential`) is a controlled-vocabulary individual representing a role or qualification a CMS policy affirmatively requires of a service or test performer — for example "treating practitioner", "treating clinician", "Independent Diagnostic Testing Facility (IDTF)", "qualified laboratory", "Part A provider". The full set of established individuals lives in the graph (`GEM_policy_instances.ttl`, subjects typed `gem:ProviderCredential`), which is authoritative for their meanings via `gem:prefLabel` / `gem:description`; a new credential individual is recorded there at extraction time, not in a separate registry. `gem_reference.md §2e` documents the class, its conventions, and the term-distinctness guidance.

**Term-by-term distinctness.** Credential individuals are kept distinct by **meaning**, not surface similarity. The "treating practitioner" / "treating clinician" pair is the canonical example: in CMS's term of art the former denotes a non-physician (nurse practitioner, clinical nurse specialist, physician assistant) and the latter denotes anyone clinically qualified (M.D., D.O., NP, or other allied health professional) — a subset/superset relationship, not synonymy. See `gem_reference.md §2e` for the full distinction; the operational consequence is the routing rule below.

**The strict-prose rule — when a mention licenses a link.** A policy's mention of a candidate credential role licenses a `gem:requiresProviderCredential` link only when the policy's **current prose** (Revision History excluded per the three-contexts rule) names the role as the *performer or evaluator of a required step* — ordering or evaluating a clinical test, qualifying the patient under coverage criteria, prescribing or signing for the equipment. Mentions where the role appears only as a passive subject of recordkeeping ("documentation must include the treating practitioner's signature") do **not** license a link — these are documentation requirements about the role, not coverage requirements that the role be present. (Scope narrowed 2026-06-03, Session 35; precedent: A52466 BR1 link removed because the only current-prose mention of "treating practitioner" was in a documentation-requirement context. A52510, processed S36, had no current-prose mention at all — only Revision History R1 — and correctly carries no link.)

**The "responsibilities for credentialed professionals" standard (S37 pass 8 broadening).** The strict-prose rule's positive duty list above (ordering, evaluating, qualifying, prescribing, signing for the equipment) names the **canonical** licensing cases, not the complete boundary. The operative test is whether the policy's current prose **mentions responsibilities for the credentialed professional** the link would point to — and that test extends past the canonical verbs to any current-prose mention of an activity, duty, or evidentiary contribution within the credentialed role's scope of practice. The mention need not use a canonical verb; the literal role-name need not appear in every sentence. A policy describing duties a credentialed professional is expected to discharge is a policy that requires the credentialed professional, regardless of how the policy phrases it.

**Worked examples — three calibrating cases:**

- **CLEAR KEEP — direct duty mentions.** L33718 contains 11+ current-prose mentions placing the treating practitioner as the clinical actor (determining medical necessity, reviewing tests, qualifying the patient). The canonical pattern; no interpretive question.
- **KEEP — clinical-judgment artifact named as the source of evidence.** A52517's only relevant current-prose mention reads *"Documentation of continued medical need ... must come from the treating practitioner's records."* The practitioner's clinical records are named as the substantive evidence base; the policy is implicitly invoking the practitioner's clinical-judgment work. Link kept (S37 pass 8).
- **KEEP — administrative-framework requirement performed by the credentialed role.** A52494 and A52495 invoke the Final Rule 1713 face-to-face encounter requirement, cross-referenced to A55426. The F2F encounter is a clinical activity performed by a treating practitioner or treating clinician; the policy's mention of the F2F requirement therefore mentions a responsibility for these credentialed professionals — even though the literal role-name does not appear in the F2F sentence itself. Link kept on both policies (A52495 from its original extraction; A52494 restored Session 39 under this standard, reversing the S37 pass 6 REMOVE that had been decided under the narrower literal reading of the rule above).

The canonical REMOVE pattern remains as illustrated in the strict-prose rule paragraph above — a pure recordkeeping artifact where the role's clinical identity is incidental (signature on documentation). The role's name on an attribution line carries no clinical activity; it is an identification, not a responsibility.

**Implications for legacy BR1-removed policies.** Three of the cycle's BR1-removed policies (A52466, A52510, A52492) had their links removed under the narrower S35 reading and have not yet been re-read against the broadened standard. Proposal #55 in the worklist queues that re-audit; given that DME articles routinely invoke Final Rule 1713 F2F (visible in A52466's policy description already), some of those REMOVE decisions are likely to reverse on re-read.

(Standard articulated 2026-06-04, Session 37 pass 8; worked examples and broadened-test text added 2026-06-05, Session 39, with Tom's direct guidance on the F2F-as-licensing pattern via A52494.)

**Routing by source phrase, verbatim.** When a credential link IS licensed, the link must route to the credential individual whose `gem:prefLabel` matches the **source phrase exactly** — never to a more common credential individual by default. Operational steps:

1. **Note the source phrase verbatim** in the Plan-turn manifest's `provider_credentials[].governing_text` field. The exact words the policy used are part of the evidence the user reviews.
2. **Match against existing individuals' `gem:prefLabel` strictly.** If the source phrase matches an existing prefLabel exactly (allowing only trivial case/punctuation differences), reuse that individual. If the source phrase is distinct from every existing prefLabel — even by a single word, even when meanings overlap — propose a new individual rather than collapsing into the closest existing one. The reuse-vs-mint decision is the user's call at Plan-turn approval. (Mirror of the "catalog phrasings; don't consolidate them" rule for clinical concepts.)
3. **Never default by frequency.** That `gemi:credentialTreatingPractitioner` is the most-linked credential in the graph (10 policies as of S36) is irrelevant to a new policy's routing. If a policy says "treating clinician", the link goes to `gemi:credentialTreatingClinician`; if it says "treating practitioner", the link goes to `gemi:credentialTreatingPractitioner`. The two are subset/superset, not synonyms.

The same procedure applies to any candidate credential phrase: "ordering physician", "ordering provider", "treating physician", "qualified medical professional", and so on — each warrants its own strict-prose check and source-phrase match, with mint-or-reuse decided at Plan-turn approval.

**Term-of-art alias.** A regulatory parenthetical in policy prose may introduce one credential phrase as a defined alias for another — e.g., "the term 'X' is defined in §<citation> as 'Y'" — declaring that 'X' and 'Y' denote the same credentialed role for the policy's purposes. When this happens, **every phrase introduced by the alias is a licensed credential mention**, even if some of the aliased phrases do not appear independently elsewhere in current prose. The regulatory gloss is the source's own assertion that the phrases co-refer; the strict-prose rule reads them as if all were present in prose, because the source has explicitly authorized that reading. Each aliased phrase is minted (or reused) as its own credential individual per the catalog-phrasings rule, and each receives a `gem:requiresProviderCredential` link from the citing policy. Worked example: NCD 210.1 §C's parenthetical regulatory gloss aliased three phrases — "attending physician", "beneficiary's physician", and "doctor of medicine or osteopathy" — as denoting the same credentialed agent for the policy's purposes; all three were minted as credential individuals and linked from NCD 210.1. (Rule established 2026-06-05, Session 41.)

**Composite-role inference for DME supplier.** A policy that heavily references DME items and uses "supplier" in the same sentence (or within a couple of nearby sentences) licenses the `credentialDMESupplier` link, even when the literal phrase "DME supplier" does not appear in continuous prose. The DME context disambiguates which "supplier" is meant; treating the two-word phrase as a strict requirement would systematically under-link DME LCDs and Articles whose prose pairs DME items with supplier obligations sentence-by-sentence. This exception is narrow to DME supplier specifically and does not generalize to other credentials — composite-role inference is licensed only where one term provides unambiguous domain context for the other and the corresponding two-word phrase is a recognized CMS role. (Rule established 2026-06-04, Session 37 pass 7, on L33718.)

**Composite agents take credential treatment.** A policy that names a multi-person team or non-individual actor as the performer of a clinical activity ("by a team", "by a panel", "by a multidisciplinary group") mints a `gem:ProviderCredential` individual at the literal source phrase, not a `gem:ClinicalConcept`. The catalog-phrasings rule applies: mint the exact phrase the policy uses. The decisive test is *grammatical positioning as the agent of clinical activity*, not whether the named role is a single individual. ("Multidisciplinary team" minted as a ProviderCredential in S39 on Tom's direction; the question "team vs. concept" was decided in favor of the credential treatment because the team is named as performing clinical work on patients.) The strict-prose / responsibilities standard above still gates whether the link is licensed; this rule only controls the *shape* of the credential individual once licensing is established. (Rule established 2026-06-05, Session 39.)

**Slash-separated role names decompose into separate individuals.** When a policy uses a slash-separated phrase for credentialed roles ("referring/ordering physician", "physician/nurse practitioner/physician assistant"), default to one credential individual per slash-separated element. The two or more roles may be filled by different people on a given claim, so each warrants its own URI for retrieval. The single-individual literal phrasing — the slash-separated source phrase — is preserved verbatim in *each* resulting individual's `gem:description` (a marker like "conveyed by the slash-separated phrase 'referring/ordering physician' in A58075" records the original wording without requiring the URI to inherit the slash). (Rule established 2026-06-05, Session 39, on Tom's direction.)

**Credential URI rename re-asserts the link under the current rule.** When a swap moves a policy's inbound credential link from a pre-rule URI to a post-rule canonical one — bridging two methodology eras — the swap is not a mechanical edit. It re-asserts the link's legitimacy under the post-rule licensing standard, and the affected policy's current prose must be verified against that standard before the swap, exactly as for a fresh extraction's credential decision. The purely mechanical framing applies only to graph-cleanup steps that commit no policy to a new claim (retiring an orphan with zero inbound links; deduplicating identical individuals). (Rule established 2026-06-04, Session 38 pass 9 verification, on L33800.)

(Methodology promoted from `deferred_proposals` #50, Session 36. The audit task recorded in #50's `note` — re-read each of the 10 policies currently linking to `gemi:credentialTreatingPractitioner` and verify the source phrase verbatim — is queued for the 20-policy checkpoint review.)

## Clinical Concepts

Code-based extraction alone leaves most of an NCD's content unrepresented: NCDs state coverage in prose, and a policy can be highly relevant to a claim through a clinical concept that carries no code at all. The **clinical-concepts category** captures that content so it can serve claim relevance: if a claim's notes mention a concept a policy refers to, the policy becomes a relevance candidate.

**What to capture (scope — "Option B").** Capture every clinical concept the policy mentions — conditions, findings, measurements, tests, therapies, drug categories, physiological concepts, and items of equipment. Err toward inclusion; the downstream medical review prunes for relevance. **Do not** capture generic administrative, billing, or document vocabulary — examples include "claim", "supplier", "beneficiary", "date of service", "medical records", "physician", "annual wellness visit", "evaluation and management service", and "global billing period for obstetrical care" — these are not clinical concepts. The test is clinical-vs-administrative, not domain-relevance: a clinical concept the policy mentions is captured regardless of which domain it "belongs" to. When uncertain whether a phrase qualifies as clinical or administrative, surface the question at Plan turn rather than guessing. (Rule simplified 2026-06-10, Session 48: the prior relational-domain test gated generic physiological terms against the policy's subject; that test is retired with the project's domain expansion.)

**Cross-reference NOTE concepts (presence, not governance).** A clinical concept named only in a navigational cross-reference — a "see §X" NOTE or Cross Reference pointer redirecting to another policy — is still captured as a `gem:ClinicalConcept` link on the referring policy. The link records the concept's **presence** in the text (Option-B / presence-not-interpretation); it does **not** assert the referring policy governs or covers it (governance lives in the pointed-to §X). Precedent: NCD 160.2's §160.24 NOTE names deep brain stimulation, essential tremor, and Parkinson's disease only to redirect the reader — all three captured on `gemi:ncd160.2` though 160.2 governs none. (Convention established 2026-07-03, Session 113; Tom-confirmed.)

**Drugs: categories yes, individual drugs only via rules.** Drug *categories* (e.g., "anticoagulants", "antibiotics", "inhaled corticosteroids") are minted as ordinary clinical concepts when the policy mentions them. *Individual* drug names (e.g., "warfarin", "amoxicillin") are NOT minted as clinical concepts by default; mint only when a `gem:ruleDescription` rule on the policy mentions that specific drug. The project may later link a formulary dataset to policies; until then, individual drugs stay out of the concept catalog by default. (Rule established 2026-06-10, Session 48.)

**How to model.**
- A concept is an individual of `gem:ClinicalConcept` (a class; `rdfs:subClassOf skos:Concept`).
- The policy links to it with `gem:refersToClinicalConcept` (object property, `gem:CMSpolicy` → `gem:ClinicalConcept`).
- **One individual per concept.** A concept appearing many times in one policy is still one individual. A concept appearing in many policies is still one individual — reused, with one `gem:refersToClinicalConcept` link from each policy it appears in.
- **Presence, not interpretation.** The link records that the concept appears in the policy. It does not assert coverage polarity and does not evaluate *how* the concept is mentioned.
- `gem:prefLabel` records the concept in the policy's own wording. The concept individual's `gem:description` carries verbatim governing text and location.

**A concept named in a non-coverage statement is still linked.** When a policy names a clinical concept only to say it is *not* covered ("the topical application of oxygen … [is] not covered"), the concept is linked with the ordinary `gem:refersToClinicalConcept` — there is no non-covered variant for concepts, and the non-coverage is **not** logged as a deferred proposal (it is an evaluation outcome, which the claim-readability test keeps out of the modeled graph). The reason to create the link anyway: the link is what makes the policy *discoverable* to a claim that mentions the concept. A claim referencing topical oxygen should surface NCD 270.4 as relevant precisely *because* that policy rules on topical oxygen — and a non-coverage determination is among the most decision-relevant things an evaluator can find. Without the link the policy is invisible to that claim and the evaluator never learns the concept is non-covered; with the link, the evaluator finds the policy and its `gem:description` governing text supplies the non-coverage fact. The link plus verbatim governing text is the complete, correct representation; polarity belongs only on codes. This holds whether the non-covered concept is the policy's only domain hook (as in NCD 270.4) or one of many.

**What is deliberately deferred.** Concept-to-concept hierarchy (`skos:broader` / `skos:narrower`) and synonym consolidation are **not** done during extraction — `gem:ClinicalConcept` is a single flat class with no granularity subtyping. Near-synonyms ("PO2", "partial pressure of oxygen") and obvious parent/child pairs ("home oxygen", "home oxygen equipment") are kept as separate individuals; building the taxonomy is a later, human-reviewed pass. Extraction's job is to find and record concepts, not to organize them — the same division of labor as "never guess a code": structure that requires clinical judgment belongs to the human reviewer.

**Composite concepts are captured whole, and their word-parts are not minted from them.** A policy sometimes names a concept whose label is composed of words that also appear as (or could be) other concepts — e.g., "nocturnal oxygen desaturation" or "exercise oxygen desaturation". Capture the composite as its own `gem:ClinicalConcept` individual: it carries meaning beyond the sum of its parts (a setting applied to a finding) and a provider note may use exactly that phrase. **Do not** fabricate constituent concepts ("nocturnal", "oxygen desaturation", "exercise") merely because they appear inside a composite's name. A constituent becomes its own individual only if the policy names it independently as a concept in its own right. Flag composites in the Plan manifest (`composite_flag`) so the SME can later decide whether to relate them to constituents — that relating is part of the deferred taxonomy pass, not extraction. (Rule established 2026-05-28.)

**Why near-synonyms are minted separately — the single-term-linkage rationale.** Keeping near-synonyms as distinct individuals is deliberate, not a deferral of cleanup. The matching objective is: a single concept term should be sufficient, on its own, to link a claim to a policy. If "PO2" and "partial pressure of oxygen" are separate individuals and a policy links both, then a provider note containing *either* phrasing independently produces the claim→policy link — the matcher never has to recognize that two terms are the same thing to make a connection. Redundant single-term coverage is therefore a *feature*: it maximizes recall in claim→policy matching. Consolidating synonyms into one individual would, by contrast, make recall depend on the matcher's own synonym knowledge. Hierarchy and peer relationships are left entirely to the later SME taxonomy pass; the reuse-vs-mint decision on each near-synonym is made by the user at the Turn-1 checkpoint, with mint-new as the default recommendation.

**Catalog phrasings; don't consolidate them.** The reason near-synonyms are minted separately is not that we haven't decided yet whether they're the same — it's that we explicitly want both phrasings preserved as distinct individuals. The ontology is a *catalog* of how meanings are communicated in policies and provider notes, not a normalized vocabulary. When an SME later determines two individuals refer to the same underlying concept, the resolution is an equivalence assertion between two retained individuals (e.g., `skos:exactMatch`, `skos:closeMatch`, or analogous predicate) — never a collapse of one into the other. A reuse decision made on similarity grounds at extraction time loses a fact about how the policy expressed itself, and that loss cannot be recovered later. The default is therefore: when in doubt, mint; when not in doubt but the phrasings differ, also mint. Reuse requires that the policy's wording match an existing concept's prefLabel exactly (or near-exactly — trivial case/punctuation differences only). Anything beyond that — a word dropped, a different noun, plural vs. singular, acronym vs. full-form when the existing prefLabel uses only one of those — defaults to mint. (Rule established 2026-05-30, Session 27 during L33800's Plan turn, after a pattern of consolidation-by-similarity proposals.)

**Section headings are a mint/reuse site, not only the operative sentences (Tom, S157).** A concept named in a section *heading* is named by the policy, and the catalog-phrasings rule reaches it exactly as it reaches prose: the heading is CMS's own name for what the section is about. Mint it, or reuse an existing individual if the heading matches its `gem:prefLabel` under the reuse test above. **A heading and its operative sentence commonly yield two individuals, and that is correct rather than redundant** — the heading names the thing at one granularity and the sentence usually narrows it with the qualifiers the coverage actually turns on; both are phrasings the policy uses, and both are wanted. Worked example, NCD 280.14 (S157): §B.2.c's heading *"Opioid Drugs for Treatment of Chronic Intractable Pain"* reproduces the existing `gemi:conceptChronicIntractablePain`'s prefLabel exactly and **reuses** it, while the section's operative sentence (*"…severe chronic intractable pain of malignant or nonmalignant origin…"*) **mints** its own individual, because *severe* raises the threshold and *of malignant or nonmalignant origin* expressly opens the indication beyond cancer. The parallel §B.2.b heading (*"Anti-Spasmodic Drugs for Severe Spasticity"*) reuses `gemi:conceptSpasticity` alongside a minted `gemi:conceptChronicIntractableSpasticity`. **The rule exists because the corpus did both, in adjacent sections of one policy, before anyone wrote it down** — NCD 280.14's Plan-turn manifest carried §B.2.b's heading reuse and missed §B.2.c's, and the miss was only visible because the two sections are structurally identical. Headings do not license concepts the section's content does not support: this rule governs *whether a heading may be a source phrase* (it may), not the Option-B scope rule, which still decides what counts as a clinical concept at all. (Rule established 2026-07-17, Session 157; the omission it corrects is recorded in `gem_rule_categories.md` ### NCD 280.14.)

**A document title is not a section heading (Tom, S158).** The rule above reaches *section* headings — CMS naming what a section is about. A document's **title** names the **policy**, and the policy individual already carries it verbatim as `gem:prefLabel`; it is not a concept mint site, even when it names the policy's subject at a phrasing no individual in the graph holds. Worked example, NCD 280.16 (S158): the title *"Seat Elevation Equipment (Power Operated) on Power Wheelchairs"* is the device's **third** phrasing in reach of one policy — beside §A's *"power seat elevation equipment"*, which mints `gemi:conceptPowerSeatElevationEquipment`, and NCD 280.1's *"Seat Elevation Equipment (power-operated) on Medicare Covered Power Wheelchairs"*, which is an existing individual — and it mints nothing. **Know the counter-argument, because the rule's *reason* reaches further than its text:** a title is CMS naming the thing at least as authoritatively as a heading does, so *"a heading is CMS naming the thing"* arguably reaches a title *a fortiori*. It does not, and the reason is what the rule turns on — **the title's subject is the policy, and a policy is not a clinical concept.** The title's *referent* still gets its individual, from the operative prose that names it; the title itself is already captured, on the policy. (Rule established 2026-07-17, Session 158; the decision is recorded in `gem_rule_categories.md` ### NCD 280.16 B8.)

**Singular normalization with plurality-only collision reuse.** When a clinical concept appears in a policy in plural form — typically inside a plural-list context like "cutaneous, decubitus, and stasis ulcers" — convert it to singular form before minting. The singular form becomes both the `gem:prefLabel` and the basis for the URI (e.g., "stasis ulcers" → prefLabel "stasis ulcer", URI `gemi:conceptStasisUlcer`). If singular normalization produces a URI that already exists in the graph, reuse the existing individual — **but only when the existing URI's label matches the new singular label except for plurality**. URI collisions arising from any other cause (two distinct concepts coincidentally producing the same camelCase form, or any other accident of label-to-URI generation) are **not** auto-reuse cases; they are surfaced as a borderline decision at Plan-turn approval for SME review. Pre-existing plural-form individuals already in the graph (e.g., `gemi:conceptAutoTitratingCPAPDevices`) are not retroactively renamed; the singular rule governs **new** mints, and an existing plural URI is reused as-is when the new policy's wording is the singular equivalent. Worked examples from TN 48 (S43): *plurality-only collision reuse* — TN 48 §40.2's "blood glucose monitor" was minted as singular; the URI `gemi:conceptBloodGlucoseMonitor` already existed (introduced earlier with the plural label "Blood Glucose Monitors", a table-source vestige); the difference was plurality-only, so the existing individual was reused. *Non-collision distinct mint* — TN 48's "stasis ulcer" generated `gemi:conceptStasisUlcer`, which did not collide with the existing `gemi:conceptVenousStasisUlcers` (different words → different URIs); the two were kept as distinct individuals per the catalog-phrasings principle, with any future equivalence assertion left to the SME taxonomy pass. (Rule established 2026-06-07, Session 43.)

**Gap in that rule as written, and how to read it (S152).** It states its test as a *URI collision*, but its rationale is a *plurality-only label difference*, and the two come apart on individuals minted before the rule, whose URIs are themselves plural. `gemi:conceptVenousStasisUlcers` (prefLabel "venous stasis ulcers", minted at NCD 280.6) is the case: normalizing NCD 270.1's "venous stasis ulcers" to singular yields `conceptVenousStasisUlcer`, which does **not** collide — so the letter of the rule mints a singular twin of an individual differing from it only in plurality. The same shape hit `conceptVenousUlcers`. A word-order variant does it too: `gemi:conceptNutritionalStatusOptimization` was minted at TN 48 §20.29 **from the phrase "optimization of nutritional status"** — the exact phrase NCD 270.1 uses — but normalized on the way in, so an exact-prefLabel-match test fails against the very wording that produced it. **Read the rule by its rationale: reuse when the only difference between the source's wording and an existing individual's prefLabel is plurality, or when the existing individual was demonstrably minted from this same wording.** Tom confirmed all four reuses at S152. This does not soften the catalog-phrasings principle — genuine phrasing differences are still minted, and NCD 270.1 minted seven of them alongside these four reuses. Pre-rule plural URIs are still not retroactively renamed.

**Pronominal back-references are not mint-triggers.** §270's strict-mint rule was written for self-contained phrasings — a policy saying "single-level CPAP device" vs. another saying "single-level continuous positive airway pressure (CPAP) device" both stand on their own and the two phrasings are minted separately. Pronouns are different. When a policy says "hospitals certified to do such tests" with "such" referring back to "home sleep test" two sentences earlier, the entity being credentialed is the same as one already minted from "hospitals certified to do sleep tests" — the policy is avoiding repetition, not naming a different concept. Reuse the existing individual; do not mint a separately-labelled "hospitals certified to do such tests" entity that would only be coherent with its source paragraph attached.

**Claude extracts terms; the SME models them. (Applies to concepts and credentials.)** Whether two near-synonyms should be one individual or two, whether one policy's credential role matches another policy's credential role, granularity choices that affect downstream claim-matching — all of that is the subject-matter expert's work, decided at Plan-turn approval and in later review passes. Claude's extraction-time job is to capture what each policy says, in its own wording, and propose mint-or-reuse. Plan-turn and manifest descriptions of concepts and credentials describe what the source policy says about the term and stop there. They do not include arguments for mint vs. reuse, distinctions from prior policies' terms, or rationales appealing to lexical fidelity vs. consolidation. The list of proposed terms is the proposal; the user approves or amends. Lexical or semantic similarity between a policy-stated term and an existing concept is not grounds for reuse — see "Catalog phrasings; don't consolidate them" above. Even when meanings are clearly equivalent, distinct phrasings are minted as distinct individuals; equivalence between them is an SME assertion made later between two retained individuals, never a concept-collapse at extraction.

**The concept-review list.** The set of `gem:ClinicalConcept` individuals and their policy links *is* the concept-review list — a medical professional reviews these in the graph for relevance. There is no separate worklist mechanism for clinical concepts.

**Relationship to the retired `uncoded_clinical_concepts` worklist.** Earlier versions of this skill routed prose clinical concepts to a worklist list called `uncoded_clinical_concepts`. That list is **retired**: clinical concepts now go straight into the graph as `gem:ClinicalConcept` individuals. Worklists generated before the retirement keep their existing `uncoded_clinical_concepts` entries as a historical record (processed work is never deleted), but no new entries are added to it.

## Healthcare Settings

A policy that names a place of care — the home, a physician's office, an outpatient hospital department, a clinic — gets a setting link, the same way it gets clinical-concept links. Settings were the vocabulary that drifted precisely because no extraction step named them (work item [95]); this section is that step.

**What to capture.** Every place of care the policy's text names, whether as a locus of furnishing ("covered in the home"), a device-suitability referent ("designed for home use"), or an exclusion trigger ("furnished in a physician's office"). The setting *individual* names a place and nothing more; the *link* carries coverage polarity (see below), and the finer statement-kind distinction — "designed for home use" versus "covered in the home", place-of-service codes, type of bill — stays in the referencing rule's verbatim text.

**How to model.**
- A setting is an individual of `gem:HealthcareSetting` (`rdfs:subClassOf skos:Concept`), living in `GEM_policy_instances.ttl`'s HEALTHCARE SETTING INDIVIDUALS section.
- **The link carries polarity (S197).** Settings take the same covered/non-covered treatment as ICD-10 and HCPCS codes, because a claim carries a place of service and does not carry a clinical concept — settings are claim-matchable, so they follow the code model, not the polarity-free `gem:refersToClinicalConcept` model. Three sub-properties of `gem:refersToHealthcareSetting`, one link per policy per setting:
  - `gem:excludesHealthcareSetting` — **Tier 1, denial stated** for that setting. NCD 160.7.1: electrical nerve stimulation furnished by a physician in the office, by a physical therapist, or by an outpatient clinic is *excluded from coverage* by §1862(a)(1).
  - `gem:exclusivelyCoversInHealthcareSetting` — **closed list**: the source declares the named settings the entire permitted set. TN 2476: contractors shall pay G0445 *only when* the place of service is Physician's Office, Outpatient Hospital, Independent Clinic, or State or local public health clinic.
  - `gem:coversInHealthcareSetting` — **Tier 2, covered or silent**, the default for everything else.
  **The subject is normally the `gem:PolicyRule` that makes the statement**, since polarity is rule-scoped; the domain is `union(CMSpolicy, AnchoredCodingScope, PolicyRule)` for the cases that are not.
- **The policy keeps its own presence link.** `gem:refersToHealthcareSetting` continues to be asserted directly on the policy for every setting its text names — it answers *does this policy name the setting*, which is a different question from *what does this rule say about it*. It is the polarity family's parent, but the two do not derive from each other: a rule's statement is **contained** in its policy, not propagated to it, so a rule-subject polarity link entails nothing about the policy. Both are observed at extraction. (Where a polarity link does carry a policy subject, entailment supplies the parent as normal.) The 34 pre-S197 presence links are correct as they stand and need no revision.
- **A negative sentence that names a setting is not automatically an excluded setting.** The test is whether the denial attaches to the *place*. NCD 280.8's "Home use of the air-fluidized bed is not covered under any of the following circumstances" keeps the home on `gem:coversInHealthcareSetting`: the home is the covered locus and the exclusion is conditional. NCD 160.7.1's carve-out attaches to the place, so it is Tier 1.
- **The same setting may carry opposite polarities in different rules of one policy, and that is not a conflict.** Because the links hang off rules, each is a statement about its own rule and nothing is contradicted. NCD 160.7.1 is the worked example: r9 (`settingDefinition`) puts PENS, a diagnostic procedure, only in the physician's office, clinic, or hospital outpatient department; r12 (`frequency`) sets the one-month trial period and r13 the documentation boundary beyond the first month; r14 (`coverageScope`) moves continuing therapy to the home; r15 (`nonCoverage`) excludes treatment furnished in the office or outpatient clinic under §1862(a)(1). The physician's office is exclusively-covered on r9 and excluded on r15 — different service, different phase. NCD 240.2's r20 (initial coverage limited to 90 days) and r21 (renewal if medically necessary) are the same two-rule shape without settings. §Polarity rule 6 still governs a genuine conflict *within one rule*; it does not apply across rules. **Do not synthesize the phase sequence into the graph** — the ordering is assembled by a reader across r9/r12/r13/r14/r15 and no single rule states it. `gem:ruleType_settingDefinition` is defined as "what setting is required (positive definition + exclusions)", so the vocabulary already anticipated a rule carrying both polarities.
- `gem:CoverageExclusion` / `gem:excludedHealthcareSetting` are **not** the mechanism. They belong to the deferred structured coverage-outcome layer of `deferred_proposals[72]`, whose attachment predicates have domain `gem:CoverageOutcome` and zero individuals, so nothing can reach a policy through them. Do not mint them.
- **Hierarchy is `skos:broader` among the individuals**, and since S175 it is a **poly-hierarchy** rooted at `gemi:settingAnywhere` across two orthogonal axes: a **facility axis** (`gemi:settingInstitution` over hospital / clinic / hospice and their named types) and an **episode axis** (`gemi:settingInpatient`, `gemi:settingOutpatient`). A place that is both — e.g. `gemi:settingOutpatientHospital` (`skos:broader` both `settingHospital` and `settingOutpatient`) or `gemi:settingInpatientHospital` — carries an edge to each axis, so a member may have **more than one parent**. There are no setting subclasses (the S117 `gem:ClinicSetting` subclass was retired at S152, work item [95]). Assert **direct** parents only with `skos:broader`; ancestor closure (`skos:broaderTransitive`) is left to OWL entailment, so do not add a redundant edge to a grandparent already reachable through a parent (e.g. `settingOutpatientClinic` inherits `settingOutpatient` via `settingClinic`). Unlike clinical concepts, settings are a small closed-ish vocabulary, so the hierarchy is asserted at extraction, not deferred: when minting a new setting that is a subtype of an existing one, add the `skos:broader` edge(s) — one per axis it belongs to — in the same mint.
- **Labels and URIs.** `gem:prefLabel` is the bare place phrase — qualifier-first, no parentheses, never the word "setting" ("clinic", "outpatient hospital", "physician's office"). When the source's own place phrase carries the generic word "setting", strip it to form the label ("outpatient treatment setting" → "outpatient treatment", S220 B9). URI = `setting` + UpperCamelCase(prefLabel), punctuation dropped (`gemi:settingPhysiciansOffice`). Reuse-vs-mint follows the clinical-concept discipline: reuse on exact/near-exact label match, otherwise surface at Plan turn.
- `gemi:settingAnywhere` is reserved for an affirmative "performable anywhere / any setting" statement **only** — never attached on policy silence about setting (Core Principle #10).

**Settings are not benefit categories.** A "Skilled Nursing Facility" `gem:BenefitCategory` individual is a Medicare benefit classification; a skilled-nursing-facility setting is a place. Keep them distinct even when the words match.

**Established members (S152):** `settingHome`, `settingHospital`, `settingOutpatientHospital` (⊂ hospital), `settingPhysiciansOffice`, `settingClinic`, `settingIndependentClinic`, `settingOutpatientClinic`, `settingPublicHealthClinic` (all three ⊂ clinic), `settingAnywhere`. See `gem_reference.md` §2p.

## Policy Description Style

A policy's `gem:description` should match the policy's structural complexity. The description has to communicate the policy's scope to a reader who may not have the source document at hand; readability of that summary is a first-order concern.

- **Simple policies** — a single coverage statement, no special mechanism, no multi-Group coding structure — take a single-sentence description naming the policy's scope and (optionally) its effective date. Example: NCD 160.7's one-sentence description set during S39.
- **Complex policies** — Coverage with Evidence Development, multi-section coverage, multi-mechanism, multi-Group coding structure, dual-diagnosis requirements, jurisdictional context — take multi-sentence prose. Each substantive aspect gets its own clear claim. Example: NCD 160.18 with CED, multiple covered indications, and a non-coverage section; A58075 with three coding regimes and a dual-diagnosis requirement.

Comma-rich single-paragraph descriptions force the reader to mentally pop nested parentheticals; sentence breaks let claims terminate cleanly. When in doubt — when the policy's structure is non-trivial — prefer multi-sentence prose over a longer single sentence. (Heuristic articulated 2026-06-05, Session 39, on Tom's direction.)

**`gem:description` is for data consumers. `gem:workflowDescription` is the extraction's notepad. (Tom, S151.)**

`gem:description` says **what the entity is** — the account a consumer of the graph needs, in their terms. `gem:workflowDescription` (`owl:AnnotationProperty`, no domain/range, single-valued, ordered immediately after `gem:description`) says **how the record got here**. The split applies to every individual, not just policies.

| Goes in `gem:description` | Goes in `gem:workflowDescription` |
| :--- | :--- |
| What the entity is; its scope; its operative content | Session provenance ("promoted at S151", "minted during A52467's extraction") |
| Governing text and its location in the source | URI / manual-token derivation and its priority level |
| Verbatim source wording and source-fidelity findings a consumer must see | How a source URL was resolved, or that it is pending and why |
| Retired / retired-in-place status | Borderline decisions, the alternative considered, and why |
| Effective dates, versions, benefit categories | Cross-references to `SKILL.md`, `gem_reference.md`, `gem_rule_categories.md`, `deferred_proposals` |

**Reserved to `gem:description` by explicit scope call (S151):** schema-term change history (`gem:appliesWhenProcedure`'s "generalized from `gem:PolicyGroup` to `gem:AnchoredCodingScope` at S60") stays where it is — different audience, different lifetime, and a separate proposal if ever. Retired-status prose stays too; it is consumer information.

**Delete rather than move:** stub-pending prose ("To be populated by its own extraction pass") duplicates `gem:nextPlannedStep gem:planPromote`, which is authoritative. Moving it preserves the duplication in a new place. Drop it.

**The corpus is FORWARD-COMPLIANT ONLY.** The property was defined at S151 and NCD 240.1's individuals are the first born clean. 351 of 2,207 described subjects minted before S151 still carry workflow prose inside `gem:description` — 76/86 transmittals, 38/40 NCAs, 32/33 change requests. Do not read a pre-S151 `gem:description` as consumer-clean, and do not treat the absence of `gem:workflowDescription` on an old individual as a finding. The backfill and its `description_workflow_leak` guard are `deferred_proposals[100]`, scheduled for the 80-policy checkpoint alongside `[99]`. New mints from S151 onward split correctly at the point of minting.

## GEM Mapping

Detailed term list is in `gem_reference.md`. Summary:

**Reuse (do not redefine) — pre-existing GEM terms:**
- `gem:CMSpolicy` — the policy class. All policy instances are typed to one of its three subclasses.
- `gem:refersToICDdiagnosis` — existing policy→diagnosis property (polarity-neutral parent; see Polarity rule 4).
- ICD-10 codes are existing external IRIs in the `icd10:` namespace, e.g. `icd10:J96.11`. **Preserve the dot.** The IRI must satisfy the `gem:ICDdiagnosisShape` SHACL pattern. The skill links to the code IRI; it does not mint diagnosis individuals.

**Established project terms — already built and approved; reuse, do not re-propose:**
These were proposed and approved during the first policies and now exist in `GEM_ontology.ttl`. Treat them exactly like pre-existing GEM terms — a new policy that uses them adds zero schema terms.
- Subclasses `gem:NCDpolicy`, `gem:LCDpolicy`, `gem:ArticlePolicy` of `gem:CMSpolicy`.
- `gem:referencesPolicy` — object property, policy → policy.
- `gem:coversCondition` / `gem:excludesCondition` — sub-properties of `gem:refersToICDdiagnosis`.
- `gem:refersToHCPCSprocedure` (polarity-neutral parent) with sub-properties `gem:coversProcedure` / `gem:excludesProcedure`; and `gem:refersToHCPCSmodifier`.
- `gem:ProviderCredential` class plus controlled-vocabulary individuals (treating practitioner, qualified laboratory, Part A provider, IDTF, …), grown as policies introduce new credential concepts.
- `gem:ClinicalConcept` class and `gem:refersToClinicalConcept` property (see "Clinical Concepts").
- Policy-metadata datatype properties: `gem:publicationNumber`, `gem:manualSectionNumber`, `gem:policyVersion`, `gem:policyEffectiveDate`, `gem:policyImplementationDate`.
- `gem:AnchoredCodingScope` (abstract) and its two subclasses `gem:PolicyGroup` (documented Coding-Information Groups) and `gem:PolicyCodingRule` (prose-derived Coding-Guidelines anchor-bound rules); umbrella predicate `gem:hasAnchoredCodingScope` with sub-properties `gem:hasPolicyGroup` and `gem:hasPolicyCodingRule`; anchor predicate `gem:appliesWhenProcedure` on the abstract parent; the closed-list and exclusion predicates (`gem:exclusivelyCoversCondition`, `gem:exclusivelyCoversProcedure`, `gem:excludesCondition`, `gem:excludesProcedure`) scoped to either policies or anchored coding scopes via union domains (see §Anchored Coding Scope Modeling and `gem_reference.md` §2j).

**Proposing further terms (user approves before any schema write):** create a new class or property only when (a) no existing GEM term fits, (b) 2+ instances exist or are clearly likely across the corpus, and (c) the user has approved it in a Plan turn. New terms must follow GEM conventions exactly: `gem:` prefix, `gem:prefLabel`, `gem:description`, `gem:memberOfOntology gem:gemOntology` (second-to-last), `rdfs:domain`/`rdfs:range` on properties, `rdfs:subClassOf` on classes. When evaluating a candidate term, judge it by **meaning, not format** — a property is distinct because what it *means* is distinct, not merely because no existing name matches. See `gem_reference.md`.

**HCPCS modeling note:** the BioPortal UMLS HCPCS ontology (`HCPCS.ttl`, v2025aa) has been integrated. HCPCS procedure/item codes and modifiers were converted from `owl:Class` definitions to individuals of `gem:HCPCSprocedure` and `gem:HCPCSmodifier` (a conversion mirroring the ICD-10 work). HCPCS references therefore link to `hcpcs:` IRIs that are typed individuals, and the `gem:refersToHCPCS…` predicate ranges (`gem:HCPCSprocedure`, `gem:HCPCSmodifier`) let SHACL enforce that a modifier predicate points only at a modifier. **Preserve HCPCS local names exactly — no dot** (`hcpcs:E1390`, `hcpcs:KX`), unlike ICD-10.

**CPT modeling note (schema minted S88).** CPT codes are HCPCS Level I and are *not* in the BioPortal HCPCS dataset (which is CMS Level II only), so they come from a separate source: `cpt.ttl`, a maintained mock-up in the `cpt:` namespace (`https://www.ama-assn.org/cpt#`; IRI = bare code, e.g. `cpt:95860`), to be replaced later by a CMS-managed CPT file. **Model:** `gem:CPTprocedure rdfs:subClassOf gem:HCPCSprocedure`. A CPT code is typed `gem:CPTprocedure` by `gem_cpt_conversion.rq` (the exact analogue of `gem_hcpcs_conversion.rq`; `cpt.ttl` itself **never references the GEM ontology**), so the existing procedure axis references it with **no new predicate**: `gem:appliesWhenProcedure` (anchor) and the `gem:coversProcedure` / `gem:refersToHCPCSprocedure` family (coverage) all range on `gem:HCPCSprocedure`, which a `gem:CPTprocedure` satisfies. One query over `gem:HCPCSprocedure` returns Level I (CPT) and Level II together; "is this anchor a CPT code?" is `?c a gem:CPTprocedure`. The procedure-anchor materialization rule extends to CPT (a CPT code anchoring a scope also materializes a policy-level `gem:coversProcedure cpt:NNNNN`). **Validation graph:** like ICD and HCPCS codes, CPT codes are **not** loaded into the audit-time/SHACL validation graph; the procedure SHACL shapes validate the `cpt:` IRI form by `sh:nodeKind sh:IRI` + `sh:pattern` (never `sh:class`). The procedure patterns enforce a **strict partition**: HCPCS Level II (`[A-Z]\d{4}`) under the `hcpcs:` namespace, CPT Level I (5-digit Cat I, `####F` Cat II, `####T` Cat III) under `cpt:` — a 5-digit code under `hcpcs:` is rejected. **Extraction sub-step:** when a policy cites a CPT code absent from `cpt.ttl`, add it as a provisional individual — `a cpt:CPTCode`, `cpt:code`, `cpt:provisional true`, and the placeholder `cpt:shortDescriptor "Descriptor is copyrighted by AMA"@en`; **do not** copy the AMA descriptor (copyrighted) and do not assert `skos:broader` (heading assignment deferred to the CMS file). **Status — minted S88.** `gem:CPTprocedure` is in the schema; `cpt.ttl` is in the tracked set (hash-track only). CPT procedure references use `cpt:` IRIs; the S88 backfill re-homed the previously-extracted CPT references (A54969, tn2476, tn2677, A58075) from the `hcpcs:` 5-digit form to `cpt:`. The earlier do-not-assert guard is lifted.

**ICD-10 and HCPCS codes are never minted — external, read-only reference datasets (Tom, S183).** `cpt.ttl` is the *only* code file GEM authors, and provisional-CPT minting (the sub-step above) is the *only* code-minting exception — CPT Level I has no maintained public dataset yet. ICD-10 (`icd10:`) and HCPCS Level II (`hcpcs:`) codes come from **co-resident external reference datasets** (the BioPortal UMLS conversions; see the HCPCS and CPT notes above and the S97 co-residency note). A policy **references** such a code by its external IRI — via the `gem:coversCondition` / `gem:excludesCondition` / `gem:coversProcedure` / `gem:excludesProcedure` / `gem:refersToHCPCS…` families — but GEM never **stubs, mints, or authors** the code individual itself: its `rdf:type` and `skos:prefLabel` come from the source dataset at query time via the conversion query. (Local GEM-side annotation of an *existing* external IRI is a different, permitted thing — see "Local annotation of external code IRIs" below.) **Consequence — the `HCPCS.ttl` "15th canonical file" question resolves to _no_ (closes handoff §4 item 10):** because GEM authors no HCPCS individuals, there is no GEM-maintained HCPCS Turtle file to track; the HCPCS dataset stays a co-resident reference dataset, outside the canonical set and the audit `TTL_FILES`, exactly as the S97 note records. `cpt.ttl` is the sole code file in the tracked set precisely *because* CPT is the sole mint exception.

**Instance namespace:** policy instances and the individuals minted by this skill (credentials, clinical concepts, qualification groups, cited-policy stubs) use the `gemi:` namespace (`http://www.cms.hhs.gov/ontology/2026/07/GEM/instances/`), kept distinct from the `gem:` schema namespace. External code IRIs keep their own namespaces (`icd10:`, `hcpcs:`, `cpt:`).

**Local annotation of external code IRIs.** When information about an external code is useful but the source ontology doesn't carry it — e.g., a Medicare-specific semantic meaning for a HCPCS modifier, a coding-clarification note on a particular HCPCS procedure code, or an interpretive flag on an ICD-10 diagnosis — annotate the external IRI directly with a GEM-namespace predicate. The external IRI's `rdf:type` continues to come from the source ontology at query time via the conversion query; the annotation predicate's `rdfs:domain` may reference the GEM class (e.g., `gem:HCPCSmodifier`) consistent with the conversion query's typing. This is *local annotation*: we are documenting GEM-side information about the term without redefining the term itself. Established use: `gem:modifierSemantics` on `hcpcs:KX` / `hcpcs:GA` / `hcpcs:GZ` (S40 Bucket 3b promotion — vocabulary-level semantic strings for the three coverage-criteria-met / ABN-status modifiers). The pattern extends to additional modifiers and to other external code systems when there is information the publisher did not encode that the project wants to record. (Pattern recognized 2026-06-05, Session 40.)

**The dc:source rule (GEM-specific — differs from the generic turtle-style-guide).** GEM does **not** mint source-document individuals and does **not** use the `schema:` prefix or `schema:Book`. Instead:
- A **policy individual** (anything typed `gem:CMSpolicy` or a subclass) takes the **document's URL** as a plain IRI in `dc:source` (e.g., `dc:source <https://www.cms.gov/medicare-coverage-database/view/ncd.aspx?NCDId=169>`). This includes cited-policy **stubs** — a stub is a policy, so its `dc:source` is its *own* document URL.
- **Every other minted individual** (clinical concept, provider credential, qualification group) takes the **`gemi:` URI of the policy whose extraction introduced it** (e.g., `dc:source gemi:ncd240.2`).
- A **reused** individual keeps the `dc:source` of the policy that first introduced it; later appearances are recorded only by the new `gem:refersTo…` link, never by changing `dc:source`.
- If a policy's URL is unknown, do **not** invent or omit it — stop and ask the user for the URL.

See `gem_turtle_style_guide.md` for the full formatting rules; the dc:source convention there is authoritative.

**Acronym-preserving local names.** When minting a `gemi:` local name from a label, preserve all-caps acronym tokens (length ≥ 2): `EKG` → `gemi:conceptEKG`, `PO2` → `gemi:conceptPO2`, `P pulmonale on EKG` → `gemi:conceptPPulmonaleOnEKG`. Policy URIs preserve section-number dots (`gemi:ncd240.2`).

**Parenthetical handling in URIs.** When a label contains a parenthetical, the URI either includes or drops the parenthetical's content based on its character composition. **Include** the parenthetical iff it matches the *qualifier* pattern: first character is lowercase a–z AND content limited to lowercase letters, spaces, commas, and hyphens. **Drop** the parenthetical otherwise — acronym, eponym, and marker patterns all fall through to drop. The `gem:prefLabel` always retains the parenthetical verbatim regardless of URI treatment. Worked examples from TN 48 (S43): qualifier — `skin burn (thermal)` → `gemi:conceptSkinBurnThermal` (include); acronym — `vectorcardiogram (VCG), with or without ECG; with interpretation and report` → `gemi:conceptVectorcardiogramWithOrWithoutECGWithInterpretationAndReport` (drop); eponym — `capillary fragility test (Rumpel-Leede)` → `gemi:conceptCapillaryFragilityTest` (drop); marker — `HIV-1 core antigen (p24) test` → `gemi:conceptHIV1CoreAntigenTest` (drop). (Rule established 2026-06-07, Session 43.)

**Distinguishing-parenthetical collision rule (§634 amendment).** When the §634 drop rule would produce a URI that collides with another concept's URI within the same Plan-turn manifest, the parenthetical content is **relocated to the URI's leading position** rather than being dropped — preserving the clinically-meaningful distinction. The `gem:prefLabel` still retains the original parenthetical form verbatim. Worked examples from A54969 (S58): `Tarsal Tunnel Syndrome (Bilateral)` → `gemi:conceptBilateralTarsalTunnelSyndrome` (parallel `…(Unilateral)` → `gemi:conceptUnilateralTarsalTunnelSyndrome`); `Pain, Numbness or Tingling (Bilateral)` → `gemi:conceptBilateralPainNumbnessOrTingling`; `Weakness, Fatigue, Cramps or Twitching (Focal)` → `gemi:conceptFocalWeaknessFatigueCrampsOrTwitching`. The rule fires **only** on intra-manifest collision; an isolated distinguishing parenthetical with no colliding partner still falls under §634's drop rule. Rationale: §634 was designed for parentheticals carrying secondary metadata (acronym expansions, eponyms, regulatory markers), not for parentheticals that carry discriminating clinical facts (laterality, focality, severity). A naive drop on the latter silently consolidates two distinct concepts; the relocate keeps both URIs as valid camelCase while preserving the catalog-phrasings principle (see §Clinical Concepts → "Catalog phrasings; don't consolidate them"). (Rule established 2026-06-15, Session 58.)

**Copyright note:** HCPCS/CPT *code descriptions* are AMA-copyrighted (hence the MCD license gate). The alphanumeric **codes themselves are facts** and are freely linkable — that is what the ontology needs. Do not copy long AMA code-description text into the TTL. Governing-text snippets recorded on clinical concepts and codes must be the policy's own (public-domain US-government) sentences, not AMA description text.

## File Layout Conventions

Every policy block in `GEM_policy_instances.ttl` follows a standard banner pattern. The convention is the **A52466 pattern** (S35-confirmed; reinforced in S36 pass 4 for A52467 introducing new credentials) — every new extraction and every migration of an older block conforms to it.

**Policy header — 5 lines of `=` rules (76 chars wide):**

```
# ============================================================================
# POLICY: <PolicyID> -- <Title>
# <Document type info, revision label, effective date>
# ============================================================================
```

**Sub-banners — 3 lines of `-` rules (76 chars wide):**

```
# ----------------------------------------------------------------------------
# <SECTION NAME>
# ----------------------------------------------------------------------------
```

**Sub-sections, in this order; a sub-section appears only if that category has content for the policy:**

1. `POLICY INSTANCE` — always present; contains the `gemi:<localname> a gem:CMSpolicy` definition and all its outbound predicates.
2. `POLICY GROUP INDIVIDUALS (new mints from <PolicyID>)` — only when this policy mints `gem:PolicyGroup` instances. Positioned between POLICY INSTANCE and the next sub-section (analogous to QUALIFICATION GROUP INDIVIDUALS in policies that use that section).
3. `PROVIDER CREDENTIAL INDIVIDUALS (new mints from <PolicyID>)` — only when this policy introduces new `gem:ProviderCredential` individuals. A policy that only *reuses* existing credentials does not get this sub-section.
4. `CLINICAL CONCEPT INDIVIDUALS (new mints from <PolicyID>)` — only when this policy introduces new `gem:ClinicalConcept` individuals.
5. `POLICY STUB(s) (cited by <PolicyID>, not yet extracted)` — only when this policy introduces stub instances for policies it cites that the worklist has not yet processed. Singular `STUB` or plural `STUBS` agrees with count.
6. `ANNOTATION-ONLY STUB(s) (annotation-only, cited by <PolicyID>)` — only when this policy mints stubs that are not expected to be fully populated by their own extraction passes (the *asymmetric-stub pattern*: stubs for documents whose content does not contribute to extractable coverage data, used as a citation target for context). Distinct from POLICY STUB(s) in that the latter expects future population; ANNOTATION-ONLY STUB(s) exists purely to make the citation resolvable. Singular `STUB` or plural `STUBS` agrees with count. Established uses: NCA stubs for CAG-00313R / CAG-00313R2 cited by NCD 160.18 (the NCD is the authoritative coverage statement; the NCAs are deliberative analysis); complementary-LCD stub for L38276 cited by A58075. **The NCD-complement use is retired (S147).** The three NCDs cited by NCD 160.7 and filed here — NCD 160.2, NCD 160.7.1, NCD 30.1 — have each since been fully extracted, so the classification was wrong on every instance it ever had: an NCD cited by another NCD is a coverage statement in its own right and its content is extractable by construction. All three carried `gem:planPromote` while sitting under a header asserting they would never be populated, and NCD 30.1's own `gem:description` said "to be populated by its own extraction pass" — the block contradicted its header for 33 sessions. **The tell is the mismatch, not the roster:** an ANNOTATION-ONLY stub's workflow state must be `gem:planNone`; a stub filed here with `gem:planPromote` is misfiled by definition, and that is a mechanical check on the graph rather than a claim maintained in this prose. Slot 6 now holds only genuinely non-extractable citation targets (deliberative NCA analysis; complementary LCDs cited for context).

**The "mints in introducing section" principle.** Individuals minted from a policy live in *that policy's* per-policy sub-section, never in a global section. A stub minted because policy P cites policy P′ lives under P's POLICY STUB sub-section (P is the introducer), not under a globally-flat stubs section. The principle preserves locality: every individual sits with the extraction context that produced it, and global sections do not accrete unrelated content over time.

**Deprecated forms.** Pre-S35 banners using `# PROVIDER CREDENTIALS (new this policy)` or analogous "(new this policy)" wording are deprecated. Migrations relabel to the `(new mints from <PolicyID>)` form. Globally-flat sections of mint-from-policy individuals are deprecated; the mints-in-introducing-section principle replaces them.

**Banner content discipline.** Section-banner comments in `.ttl` files contain document-intrinsic identity facts ONLY, and every banner item must also be a queryable graph attribute. A banner does not carry data that is not also asserted as a triple elsewhere. Three corollaries:

1. **No provenance in banners.** Phrases like "Stub minted by NCD 240.2", "full extraction", session numbers ("S46 cleanup"), or extraction dates (`# Extracted: <YYYY-MM-DD>`) do not belong in banners. Provenance lives in dedicated graph properties established for that purpose (e.g., `dc:source` for the introducing policy; workflow-state properties for extraction status). Only when no dedicated property fits does provenance go in the individual's `gem:description` prose — and never in a section header. The `# Extracted: <YYYY-MM-DD>` line is a specific deprecated form — pre-S46 banners and the pre-S49 banner template both carried it, and it is removed during any reprocessing pass that touches the banner (see §Two-Turn Workflow → Reprocessing protocol).
2. **No cross-document relationships in banners.** A banner does not say "rescinded by TN 13808" or "supersedes A52514"; those are policy-to-policy facts that belong as graph triples (`gem:revisesPolicy`, `gem:revisedByPolicy`, `gem:referencesPolicy`). The banner identifies the section's subject, not its relationships.
3. **Banner items are queryable.** Every fact a banner asserts is recoverable from the graph. A reader with only the graph (no banner) can rebuild any banner from triples; a banner containing banner-only data violates the rule.

The principle: banners are minimal human-orientation aids; the graph is the source of truth. Banner-as-canonical-source is a structural error — it makes the graph incomplete relative to the file and creates two places where the same fact can drift apart.

(Rule established 2026-06-08, Session 46.)

(Convention formalized 2026-06-04, Session 37 pass 7.5, codifying the A52466 / A52467 patterns established in S35 / S36 and the layout work tracked in `deferred_proposals` #51 and #53. Slot 6 ANNOTATION-ONLY STUB(s) added 2026-06-05, Session 40, codifying the S39 asymmetric-stub pattern as part of the #53 resolution.)

## Anchored Coding Scope Modeling

An **anchored coding scope** (`gem:AnchoredCodingScope`, abstract) is a structural rule-organization unit inside a CMS Policy that anchors to one or more HCPCS procedure codes (via `gem:appliesWhenProcedure`) and scopes a set of coverage, medical-necessity, or coding-correctness assertions to claims carrying the anchor's procedure code. The abstract parent has two concrete subclasses, distinguished by their source pattern:

- **`gem:PolicyGroup`** — the *documented* anchor-scope variant. A Group as published by CMS in a policy's Coding Information section, typically pairing a "For HCPCS codes X, Y, Z:" anchor with a closed list of ICD-10 codes that support medical necessity for those HCPCS (or, in the Group 1A pattern, a list of ICDs explicitly excluded for those HCPCS).
- **`gem:PolicyCodingRule`** — the *prose-derived* anchor-scope variant. An anchor-plus-boundary statement drawn from a policy's Coding Guidelines section (or comparable prose), expressing a coding-correctness rule scoped to a HCPCS anchor — e.g., "When billing for [anchor code], do not also bill [other code]."

The umbrella predicate `gem:hasAnchoredCodingScope` links a policy to either subclass; its sub-properties `gem:hasPolicyGroup` and `gem:hasPolicyCodingRule` narrow by subclass. Anchor-scope rules can be **positive** (closed-list coverage via `gem:exclusivelyCoversCondition` / `gem:exclusivelyCoversProcedure`) **or negative** (denials via `gem:excludesCondition` / `gem:excludesProcedure`); the S60 domain extensions make all four predicates available on both subclasses.

### Policy Groups

A **Policy Group** (`gem:PolicyGroup`) is the documented anchor-scope variant: a structural rule-organization unit published by CMS in a policy's Coding Information section. Multi-Group Articles such as A52466 organize their Coding Information into one or more Groups, each pairing a "For HCPCS codes X, Y, Z:" anchor with a list of ICDs that support medical necessity for those HCPCS. The Group structure is the unit at which the source asserts the ICD constraint; extracting it as a first-class graph entity preserves the per-anchor specificity that policy-level flattening would lose.

#### When to mint a PolicyGroup

Create a `gem:PolicyGroup` instance when EITHER (a) the policy lists one or more prerequisite HCPCS procedures that constrain the application of its medical-necessity rules — typically signaled by a "For HCPCS code(s)…" anchor in a Group Paragraph — OR (b) the policy contains more than one parallel rule-set within its Coding Information section (multi-Group Articles like A52466). A policy that has neither prerequisite HCPCS nor multiple parallel rule-sets does not need Policy Groups; its rules are asserted directly at policy level.

Single-Group policies with prerequisites (e.g., A52510 with its one Group anchored to HCPCS E0482, A7020) DO get a Policy Group instance — the anchoring structure is the reason to mint, not the count. Multi-Group policies get one Policy Group per parallel rule-set in the source.

#### URI minting for Policy Group instances

Form: `gemi:<policyLocalName>_group<N>`, where `<policyLocalName>` is the parent policy's local name (`a52466`, `a52510`, `ncd240.2`) and `<N>` is the Group number as published in the source (1-indexed). Examples: `gemi:a52466_group1` through `gemi:a52466_group16`; `gemi:a52510_group1`. The underscore is a structural separator distinguishing the policy-portion from the group-portion (see §GEM Mapping / `gem_reference.md` §4 for the documented underscore exceptions).

#### Triple-writing rules for Group-structured policies

For each Policy Group:

1. Link the Group to the policy: `<policy> gem:hasPolicyGroup <group>` (on the policy). The umbrella `gem:hasAnchoredCodingScope` is reached by entailment via the sub-property declaration.
2. Anchor the Group to its prerequisite HCPCS: one `<group> gem:appliesWhenProcedure <hcpcs>` triple per HCPCS code in the Group Paragraph's anchor list.
3. Materialize the policy-level coverage of the anchor HCPCS: ALSO write `<policy> gem:coversProcedure <hcpcs>` for each prerequisite HCPCS. This is the "prerequisite HCPCS are covered" inferential rule, materialized at extraction rather than left to consumer-side reasoning.
4. Anchor the Group's closed-list ICDs: one `<group> gem:exclusivelyCoversCondition <icd>` triple per ICD-10 code in the Group's Codes list. The set's union constitutes the COMPLETE coverage scope for the Group (closed-list semantic); ICDs outside the set are implicitly excluded under that Group's anchor scope, queryable via SPARQL `FILTER NOT EXISTS`.
5. Do NOT write policy-level `gem:coversCondition` triples for ICDs that appear only inside Group Codes lists. The source-fidelity principle applies: the source asserts these ICDs only at the Group level, and the graph mirrors that. (Edge case: if a policy's Article Text or other prose names an ICD at policy level outside any Group's Codes list, that ICD does get a policy-level `gem:coversCondition` triple sourced from that mention. The principle is "write where the source asserts" — not "always Group-only".)
6. **Negative-polarity anchor-scope rules.** A Group that names ICDs or HCPCS codes its anchor explicitly excludes uses `<group> gem:excludesCondition <icd>` or `<group> gem:excludesProcedure <hcpcs>` triples — the S60 domain extensions of those predicates to `gem:AnchoredCodingScope` make this possible without a separate sibling class. Worked example: A52519's `gemi:a52519_group1a` carries `gem:appliesWhenProcedure hcpcs:A7002, hcpcs:A7047, hcpcs:E0600` and `gem:excludesCondition icd10:G47.33` — encoding the policy's "Group 1A: For A7002, A7047, E0600, G47.33 does not support medical necessity" statement.

**Cross-Group ICD duplication is preserved.** The same ICD appearing in multiple Group Codes lists yields multiple `gem:exclusivelyCoversCondition` triples (one per Group), because each is a distinct per-anchor source claim. A52466's J44.9 appears in 8 Groups, yielding 8 such triples; the unique-ICD count and the per-Group total are both derivable from the graph and both serve different queries.

#### The "DO NOT Support Medical Necessity" section

Most multi-Group Articles have a "DO NOT Support Medical Necessity" section after the Support section. Its content factors into existing predicates without structural reification, except as noted below:

- **Per-Group ICD complements** ("for the Support-section HCPCS, ICDs not listed are denied") are **implicit** in each Support Group's closed-list semantic; no triples needed.
- **Universal HCPCS blanket denials** ("for HCPCS A, B, C, all ICDs are denied") are policy-level `gem:excludesProcedure` triples on the policy. The "for all ICDs" universality is implicit in the absence of any ICD qualifier on the excludesProcedure triple.
- **Per-anchor diagnostic exclusions** ("For HCPCS X, Y, Z, ICDs A, B, C are not covered") ARE modeled as a `gem:PolicyGroup` instance carrying `gem:appliesWhenProcedure` triples for the anchor HCPCS and `gem:excludesCondition` triples for the excluded ICDs (per rule 6 above and the A52519 Group 1A worked example). This is the only DNS-content pattern that mints a Group.
- **"For all other HCPCS codes, ICD-10 codes are not specified"** is the graph's open-world default — no triples needed.

The DNS section is document organization, not assertion structure: most of its content is captured at the appropriate predicate level rather than as a minted Group.

### Policy Coding Rules

A **Policy Coding Rule** (`gem:PolicyCodingRule`) is the prose-derived anchor-scope variant: an anchor-plus-boundary statement drawn from a policy's Coding Guidelines section (or comparable prose), expressing a coding-correctness rule scoped to a HCPCS anchor. Unlike a Policy Group, a Policy Coding Rule is not published by CMS as a numbered structural unit; it is the extractor's reification of a prose statement of the form "When billing for [anchor code], the policy says [boundary statement about other codes]."

#### When to mint a PolicyCodingRule

Create a `gem:PolicyCodingRule` instance when policy prose (typically in a Coding Guidelines or analogous section) names a HCPCS anchor and asserts a coding-correctness boundary on that anchor — i.e., when the source says something equivalent to "for [HCPCS X], you may not also bill [HCPCS Y]" or "[HCPCS X] is correctly coded only when [condition on other codes]." A boundary that applies policy-wide rather than anchored to a specific HCPCS code does not yield a Policy Coding Rule — it is asserted at policy level using ordinary predicates.

#### URI minting for Policy Coding Rule instances

Form (single-anchor — the only pattern observed so far): `gemi:<policyLocalName>_<anchorCode>CodingRule`, where `<policyLocalName>` is the parent policy's local name and `<anchorCode>` is the lowercase HCPCS anchor code. Example: `gemi:a52519_a7047CodingRule` (parent A52519, anchor A7047). The underscore is the same structural separator used for Policy Group URIs. Multi-anchor Policy Coding Rules have not yet been encountered; the URI form for that case will be resolved as a borderline at first occurrence.

#### Triple-writing rules for Policy Coding Rules

For each Policy Coding Rule:

1. Link the rule to the policy: `<policy> gem:hasPolicyCodingRule <rule>` (on the policy). The umbrella `gem:hasAnchoredCodingScope` is reached by entailment.
2. Anchor the rule to its HCPCS: `<rule> gem:appliesWhenProcedure <hcpcs>`.
3. Assert the boundary using polarity-appropriate predicates. Negative boundaries (the common case — "do not also bill these other codes") use `<rule> gem:excludesProcedure <hcpcs>` per excluded code. Positive boundaries (closed-list coverage scoped to the anchor) use `<rule> gem:exclusivelyCoversProcedure <hcpcs>`. ICD-side predicates (`gem:excludesCondition`, `gem:exclusivelyCoversCondition`) are similarly available if the rule's boundary is over diagnoses.
4. The anchor HCPCS itself is materialized at policy level under the same "prerequisite HCPCS are covered" rule applied to Policy Groups: write `<policy> gem:coversProcedure <hcpcs>` for the anchor code, unless the same code is independently excluded elsewhere in the policy.
5. Optionally annotate the rule with `gem:ruleDescription` — the verbatim or near-verbatim prose statement from the source, useful when the structured triples don't fully capture the rule's wording for downstream review.

Worked example: A52519's `gemi:a52519_a7047CodingRule` carries `gem:appliesWhenProcedure hcpcs:A7047`, `gem:excludesProcedure hcpcs:E0485`, and `gem:excludesProcedure hcpcs:E0486` — encoding the policy's "When using A7047, codes E0485 and E0486 may not also be billed" statement.

## Two-Turn Workflow: Plan, then Generate

Each policy is processed in two turns, mirroring the Sherlock novel protocol. This keeps the policy text, the schema, and the instances file from competing for context, and gives the user an approval gate.

### Turn 1 — Plan

Inputs: the policy document, `GEM_ontology.ttl`, `GEM_policy_instances.ttl` (if it exists), `policy_worklist.json` (if it exists).

1. Close-read the policy (use the multi-message protocol if large). If any section is gated, stop and request a complete PDF — see "The Gate Hard-Stop Rule" — and do not produce a manifest until the full document is in hand.
2. Produce a **structured extraction manifest** (JSON, generated via Python — see Manifest Format). It captures: policy metadata; every code with context-type, polarity, and governing sentence; every modifier; every credential concept; every policy-to-policy reference; every clinical concept; deferred-proposal items; and any proposed new schema terms.
3. Present the manifest to the user as a readable summary plus the proposed schema additions. Explicitly list: codes found and their polarity, clinical concepts, uncertainties, and new terms requiring approval.
4. **Stop. Wait for user approval.** The manifest must be self-contained — Turn 2 will not have the policy text.

The approval conversation that follows proceeds one question at a time — see Core Principles #9. The manifest presents every decision in one place; the *conversational* approval works through them iteratively, not as a bundled response.

### Turn 2 — Generate

Inputs: the approved manifest, `GEM_ontology.ttl`, `GEM_policy_instances.ttl`, `policy_worklist.json`.

1. If schema terms were approved, add them to `GEM_ontology.ttl` (new terms only; preserve every existing triple).
2. Generate the policy instance and all its reference triples; append to `GEM_policy_instances.ttl`. If a referenced code, policy, credential, or clinical concept already has an individual, reuse its URI (do not duplicate). A cited policy that exists only as a stub is *populated* in place, not re-created.
3. Update `policy_worklist.json`: add new related-policy entries (`pending`), flip the just-processed policy to `processed`, append deferred proposals.
4. Run the Verification Checkpoint and present it.

**Stub promotion is part of the stub's own Generate turn, not a deferred cleanup.** When a policy that already exists as a stub is itself processed through its own Plan/Generate cycle, the fully-populated block is promoted to its own delimited top-level section *during that Generate turn* — not left in its first-citing-policy's POLICY STUBS sub-section, and not handled as a separate later cleanup pass. The promoted section gets the standard `# === POLICY: <ident> ===` header and sub-section structure per §File Layout Conventions, and is positioned at the end of the file (or otherwise integrated with the existing section order). The file-header `Policies processed:` comment is updated in the same Generate turn. The original stub location under its first-citing policy is collapsed; that citing policy's POLICY STUBS sub-section no longer references the promoted policy. The graph entity (URI, prior triples) is preserved through the move — *stub population* (adding triples while the policy remains a stub) and *stub promotion* (the move from nested sub-section to top-level section when the stub becomes fully extracted) are distinct events, and Turn 2 step 2's "populated in place" governs only the former. (Rule established 2026-06-07, Session 43; precedent: TN 48 promoted from in-NCD-210.1-section sub-block to its own delimited end-of-file section in S43 Phase B Option B Generate.)

**Dedup discipline — both sides.** Step 2 already prevents graph duplicates ("reuse its URI, do not duplicate"). The mirror rule for step 3 — the worklist side — is stated in `worklist_schema.md` ("a policy identifier appears at most once") and applies equally: before writing a new `related_policies` entry, check whether the identifier or URI is already on the worklist; if present, **enrich** rather than duplicate (append the current policy to `discovered_in`, fill any empty fields like a `source_url` resolved this session, append provenance to the `note`). The two sides can be asymmetric: a reference that pre-dated the Session-22 relaxed-scope rule may have a worklist entry without a graph stub. When such a reference is re-encountered, the correct Generate behavior is to mint the missing graph stub AND enrich the existing worklist entry — never create a second worklist entry. Precedent: NCD 240.2.1's Generate (2026-05-29) initially produced a duplicate `CAG-00296N` worklist entry because the prior NCD 240.2 pass had not minted a graph stub for it; the duplicate was caught at integrity verification and merged into the existing entry's `discovered_in`.

Use Python for any file over ~500 lines (`large-file-generation`). Preserve GEM formatting in the `.ttl` files: CRLF line endings, **spaces only** for indentation (no tabs), predicate ordering with `gem:memberOfOntology` second-to-last and `dc:source` last, definitions terminated with `.`.

### Reprocessing protocol

When reprocessing a previously-extracted policy under broadened methodology — applying methodology that did not exist at the policy's first extraction (S49 was the first such pass; see `manifest_format.md` §Reprocessing Manifests for the manifest shape) — every Generate turn includes the following methodology-gap checks **regardless of the reprocessing's stated scope**. The checks are pre-flight unconditional fixes, not borderlines:

1. **Banner discipline check.** Re-read the policy's section banner. If it contains any provenance line (`# Extracted: <YYYY-MM-DD>` is the specific deprecated form most commonly carried by pre-S46 banners) or any banner-only data not asserted in the graph, remove it. The banner conforms to §File Layout Conventions: document-intrinsic identity facts only, every item also a queryable graph attribute. Manifests record this fix as `modified.banner: true` even when the source manifest does not name the banner explicitly.

2. **S45 workflow-state check.** Verify the policy URI has `gem:nextPlannedStep` and `gem:isInEffect` asserted **somewhere in the file** — this is a **graph-level check via rdflib query**, not a block-level inspection. The file's canonical location for these triples is a dedicated **Retroactive Assignment section** (banner: "Retroactive assignment per Action 6c categorization rules", introduced 2026-06-08, Session 45). That section carries the workflow-state triples for all pre-S45 policies and stubs, sub-divided by `(planDone / isInEffect=True)`, `(planNone / isInEffect=False)`, `(planNone / isInEffect=True)`, and `(planPromote / isInEffect=True)` sub-sections with running individual counts in each header. The counts are **physical** — a sub-section's header counts the entries written beneath it, which is why they can agree while entries are logically misfiled (§4 item 6). `(planPromote / isInEffect=False)` was removed at S159: under the S159 definition of `gem:isInEffect` it is unreachable, because a document known to be deleted takes `gem:planNone`.

   If the rdflib query returns zero triples for the URI on either predicate, the policy is missing its workflow-state. Add the entry to the appropriate retroactive sub-section using the canonical two-line form (URI-lex-sort order within the sub-section, and update the parenthesized individual count in the sub-section header):

   ```
   gemi:<uri> gem:nextPlannedStep gem:plan<X> ;
       gem:isInEffect "<bool>"^^xsd:boolean .
   ```

   Values:
   - Fully extracted current policy → `gem:planDone` + `"true"^^xsd:boolean`
   - Stub awaiting full extraction → `gem:planPromote` + `"true"^^xsd:boolean` (default for newly-minted stubs)
   - Rescinded policy / transmittal / `_DELETED` stub → `gem:planNone` + `"false"^^xsd:boolean`
   - Re-examination queued by user → `gem:planRevisit` + `"true"^^xsd:boolean`

   **Do not duplicate** by also placing these triples inside the policy block; the retroactive section is the single source of truth for S45 properties. New policies/stubs minted during extraction or reprocessing follow the same convention — their workflow-state goes into the retroactive section, not into the policy block. (NCD 160.18's S49 reprocessing initially placed S45 triples in the policy block as a perceived gap, then reverted them once the retroactive-section convention was identified; S46-era transmittals tn10145 and tn10199, originally minted with in-block S45 triples in S49, were migrated to the retroactive section as part of the same correction. Both events are recorded for future sessions: the in-block placement is a recognized antipattern.)

3. **Methodology gap audit.** Any other S43 / S45 / S46 / S48+ methodology that has not been applied to the policy is surfaced in the reprocessing manifest's `borderlines` list at Plan time for the user's decision (whether to fix in this pass or defer to a future enrichment task).

Manifests record each pre-flight fix in `reprocessing_delta.modified` (e.g., `banner: true`, `workflow_state_backfilled_in_retroactive_section: true`). The first two checks are unconditional — they are applied even when the reprocessing scope does not explicitly name them — because they are part of the standard policy-file shape now and leaving them missing would compound the drift on the next pass. (Rule established 2026-06-11, Session 49.)

### The "reviewed, no action taken" outcome

A policy can be close-read in full and correctly yield **zero extraction triples** — no codes, no credentials, no clinical concepts, no policy-to-policy references. This happens when a policy turns out to have no reasonable relationship to any line of inquiry the project pursues, as determined by the user at the Turn-1 review. NCD 240.1 (Lung Volume Reduction Surgery) was the first such case — a surgical-candidacy determination with no tie to the home-oxygen line that was the project's initial focus.

This outcome is **distinct from three things it must not be confused with**: an unprocessed stub (never read), an under-extraction (read carelessly, content missed), and a gated document (content withheld). "Reviewed, no action taken" is a deliberate, complete reading whose correct result is zero. Handle it as follows:

1. **Close-read the whole document anyway.** The zero result is a finding, and a finding requires the same complete reading as any other. Apply the claim-readability test explicitly; the Plan turn states, with reasoning, that the policy yields nothing relevant under the project's current scope.
2. **Populate the stub in place.** The cited-policy stub already exists. Do not leave it reading "To be populated by its own extraction pass" — that would tell a future session the policy is still pending. Rewrite its `gem:description` to a metadata-level description that **explicitly records the deliberate zero outcome** ("Reviewed in full … found to have no reasonable relationship to the project's current scope … no clinical concepts, credentials, codes, or references were extracted — this is a deliberate no-domain-content outcome, not an unprocessed stub or an under-extraction"). Add `dc:source` if a URL is now known. Add no links and mint nothing. **Also capture any policy-metadata datatype values known from the document itself** — at minimum the current revision-effective date (`gem:policyEffectiveDate`) and page count (`gem:policyPageCount`), plus any of `gem:policyVersion`, `gem:policyImplementationDate`, `gem:publicationNumber`, `gem:manualSectionNumber` that apply and are stated in the document. These are factual metadata of the read document, independent of whether any in-domain content was extracted. Adding them costs nothing and lets a future query distinguish a deliberate-zero stub from a never-read one even without inspecting the `gem:description`. Precedent: A58247 and A55426 both carry `gem:policyEffectiveDate` and `gem:policyPageCount` on their zero-outcome stubs.
3. **`policies_processed` DOES increment.** A reviewed-and-closed queue policy is a processed policy — it was close-read end to end. This is unlike an enrichment pass (which revisits an already-processed policy and does not increment). The worklist entry flips `pending → processed` and its `note` records the no-domain-content finding.
4. **The Verification Checkpoint reports the zero honestly.** Zero counts across every category, with the self-check affirming the document was read completely. The checkpoint narrative states the zero is deliberate.
5. **References may still be *surfaced* even when they are not captured as graph links.** The zero-outcome override blocks the creation of `gem:referencesPolicy` graph links from a deliberate-zero policy, but it does **not** block worklist-supplementation. A zero-outcome policy often cites in-domain or domain-adjacent documents that the project would benefit from extracting later; capturing none of them silently would lose discovery information. In the Plan turn, list the policy's current-section outgoing references with their existing worklist status (already processed / already pending / not present). The user decides which (if any) of the not-already-present references to add to the worklist as `pending`. Any reference added this way is recorded as a worklist entry only — never as a graph link from the zero-outcome policy. The deciding rule is the user's choice, not a defaulted heuristic: ~110 references discovered in an out-of-domain process article does not mean ~110 worklist additions. The zero-outcome stub's `gem:description` records what was surfaced (or that nothing was), and each surfaced entry's worklist `note` records its §4f provenance and the source policy. Precedent: A55426 (Standard Documentation Requirements) surfaced 15 respiratory-adjacent device-category references under user direction; the other ~90 out-of-domain references were not surfaced.

**Zero triples means zero — including the policy's own transmittals, NCAs, and policy citations** (as graph links; see item 5 for the separate worklist-surfacing question). A "reviewed, no action taken" outcome **overrides** the normal "two outputs per discovered policy reference" rule (see "Policy-to-Policy References"). That rule — capture every cited NCD/LCD/Article, and every transmittal/NCA, as a graph link plus a worklist entry, regardless of the cited document's domain — exists to keep an *extracted* policy's reference web complete. A deliberate-zero policy has no reference web to complete: it yields nothing, so the documents *it* cites are not captured either. A transmittal or NCA reachable only through an out-of-domain process policy is itself an out-of-domain administrative artifact, and minting it would add reference pointers that no in-domain claim will ever traverse. Precedent: NCD 240.1 had a current-section transmittal (TN 44) and two NCAs, and NCD 310.1 had a current-section transmittal (TN 12590) and two NCAs — in both, **none** was captured. (This does not change how the *citing*, in-domain policy was handled: when NCD 240.2.1 was extracted it correctly captured its `gem:referencesPolicy` link to NCD 310.1. The override applies only to the out-of-domain policy's own outgoing references, decided at *its* extraction pass.)

The user makes the call that a policy is out of domain — surface it as a Turn-1 question with the governing reasoning, exactly as for any domain-fit uncertainty.

### Borderline handling: record-and-proceed with an end-of-policy decision tree (S91)

Established Session 91. This **supersedes per-borderline approval gating wherever it appears** — Turn 1 step 4's per-step "Stop. Wait for user approval," the "one question at a time" approval-conversation note above, the "surface it as a Turn-1 question" framing in *The "reviewed, no action taken" outcome*, and the prior one-at-a-time format. Everything else is unchanged: the two-turn structure, the manifest, the Plan/Generate context separation, the Gate Hard-Stop Rule, and the requirement that each borderline carry a concrete example (real URI, or clearly-labeled prospective URI). What changes is *when and how* borderlines are approved — at end-of-policy, in one batch, rather than per-step.

A **decision point** is each genuine borderline: capture-vs-drop, ruleType choice, granularity split, schema / new-`gem:RuleType` mint, or domain-fit (out-of-domain / deliberate-zero). During extraction Claude does **not** pause at each one. For each, Claude evaluates the best course against established guidance, **records** its recommendation with a concrete example and short rationale, and **proceeds** to the next step.

At end-of-policy Claude reevaluates the recorded decisions as a tree:

- **Independent** decisions (one choice does not change what is optimal at another) are evaluated locally, exhaustively over that decision's options.
- **Interacting** decisions are grouped into a cluster and explored over the **full cross-product** of the cluster's paths. This factored exploration replaces the infeasible full Cartesian product over *all* decision points while still surfacing every path where an earlier choice changes a later one.
- Paths are explored **analytically** — reason out each option's downstream outcome. A path's graph edits are **materialized** only where the outcome is genuinely uncertain and reasoning cannot settle it. If a materialized path reveals an interaction Claude had assumed away, it expands that cluster and re-explores.

Claude then presents the **recommended path-of-best-choices**: for each decision point, the recommended option with a **≤100-word** rationale. Architectural / irreversible calls (new `gem:RuleType`, schema changes) are **folded into this presentation**, not flagged inline mid-extraction. **Genuine ties** — borderlines with no objective best — are presented as the defensible options with Claude's lean, not forced to a single winner. Tom asks questions, then confirms or rejects; **Tom's confirmation remains required** before the path is final, and Claude does not treat its provisional in-flight calls as final. The per-policy decision log produced here **must be written in the same Generate turn that mints the policy's `gem:PolicyRule` individuals**: a `### <identifier>` section (archival stamp + rule table + borderline notes) in `gem_rule_categories.md` **plus** an Edit-log line in `gem_edit_log.md`. A promotion or rule-backfill is **not complete** until that section exists: it is a required Generate-turn edit and a Verification-Checkpoint line item, **never deferrable** to a later checkpoint or a future session. (Strengthened S120 after the S119 trio — NCD 80.11 / 140.1 / 150.5 — plus NCD 190.2 had their register sections wrongly deferred; the `register_section_coverage` audit check now enforces this.)

**A surfaced alternative must be a defensible next-best reading, not a strawman.** When Claude presents a lean plus an alternative (or the defensible options at a genuine tie), each alternative must be a real competing interpretation of the source — the option a careful reader could actually choose. An "alternative" that ignores or voids a condition the policy mandates is **not** a next-best choice; it is a failure mode. Example (NCD 190.2, B2): the policy covers a diagnostic pap smear only when the patient meets one or more of five enumerated conditions, so those conditions are an `eligibility` gate; proposing "drop the `eligibility` tag" as the alternative is invalid — it pretends the mandated conditions are absent. Claude does not manufacture alternatives for symmetry: when the lean is forced and no valid competing reading exists, Claude says so plainly ("no valid alternative") rather than presenting a strawman. (Codified S120, 2026-07-05.)

## Extraction Manifest Format

The Plan-turn extraction manifest is a structured JSON document covering policy metadata, every code with context-type and polarity, every modifier, every credential concept, every policy-to-policy reference, every clinical concept, deferred-proposal items, and any proposed new schema terms. Generate via Python (it will often exceed `file_create` limits).

See **`manifest_format.md`** in this skill folder for the full JSON schema and field-level conventions, including the `verification` block (counts, uncertainties, self-check questions) and the rule that a manifest only ever describes a complete document — a gate halts the work before a manifest is produced (see "The Gate Hard-Stop Rule").

## Verification Checkpoint

After Generate, present a report:

1. **Counts by category** — codes, modifiers, credentials, policy references, clinical concepts, deferred proposals, schema terms added.
2. **Uncertainties** — codes with uncertain polarity, ambiguous identifiers, anything flagged during reading.
3. **Schema changes** — new terms added to `GEM_ontology.ttl`, if any.
4. **Worklist delta** — entries added, the policy flipped to `processed`.
5. **Self-check questions:**
   - Every code in every coding table extracted? YES/NO
   - Every code in prose extracted with its governing sentence? YES/NO
   - Revision-history codes (and revision-history-only document citations) excluded from reference triples and the worklist? YES/NO
   - Polarity recorded for every diagnosis and procedure code? YES/NO
   - Document complete, no gated sections? YES/NO
   - Policy read completely? YES/NO
6. **File validation** — triple-delta arithmetic balances; every reference/concept/credential target resolves to a typed individual; `GEM_ontology.ttl` triple count unchanged unless schema terms were approved; zero tab characters; **zero lone-LF line endings** in the `.ttl` files (CRLF only — a lone-LF regression parses fine but violates the format rule and has occurred before); each `.ttl` file ends with `.\r\n`.
7. **Predicate histogram, not just a total (Tom, S157).** Triple-delta arithmetic is **predicate-blind** and must not be presented as the verification on its own. Project the expected **(predicate → count)** map — derived from the emitter's own structures, never hand-typed — and diff it against the actual histogram of the set-diff. Cardinality is not correctness: a projection of *"31 rules × 5 base triples + 49 ruleType = 204"* never names *which* description predicate, and S157 emitted all 31 rules with `gem:description` instead of `gem:ruleDescription` and produced **exactly 204**. The file parsed, SHACL conformed, the set-diff was clean, the total matched to the triple, and every instrument in the stack agreed the work was correct. `policyrule_completeness` caught it — but that check exists for `PolicyRule` specifically, and nothing equivalent asks whether 80 concept links landed on `gem:refersToClinicalConcept` rather than `gem:refersToHealthcareSetting`. The histogram is ~5 lines in the same script, costs nothing, and turns *"the count matched"* into *"the count matched **and every triple landed where I meant it**"* — at Generate time rather than at close. **Hand-typing the expected histogram defeats the purpose:** S157's first attempt did, got four spurious mismatches out of 25 predicates, and every one was the projection's arithmetic rather than the graph's content. Derive intent from the code that emits. (Rule established 2026-07-17, Session 157.)
8. **Programmatic Turtle parse** — Parse each modified `.ttl` file with `rdflib.Graph().parse()`; report `len(g)` and reconcile against the expected delta. A programmatic parse catches malformed escapes, unbalanced quotes, and other syntax regressions that visual inspection misses.
9. **Skill-review question** — *did this pass reveal a refinement, a new failure mode, or a missing rule that should be promoted into the skill?* If yes, propose the skill edit (see "Iterative Improvement").

If any answer is NO → flag prominently, explain, offer to redo. (A NO on "document complete" should not occur: a gate halts the work before Generate — see "The Gate Hard-Stop Rule." If it appears here, the hard-stop rule was not followed.)

## Checkpoint Cadence

Process policies **one at a time**. The first-batch dependency order — NCD 240.2 → LCD L33797 → Article A52514 — has been completed; subsequent policies are drawn from the worklist's related-policies list. ## Common Failure Modes

| Failure | Description | Prevention |
|---------|-------------|------------|
| **proceeding past a gate** | Extracting from a partially-readable document when a section is license-gated. | Gate hard-stop rule: stop, request a complete PDF, restart with the full document. |
| **revision-history-as-reference** | Creating reference triples from "Added: code X" change-log entries. | Three-contexts rule: revision history is excluded from links. |
| **polarity inversion** | Linking a denied/non-covered code with a covered predicate (or vice versa). | Per-code polarity from governing text; separate predicates; record the sentence. |
| **silent semantic reinterpretation of code polarity** | The per-code rule (§237, §240–§244) yields one polarity but the code's semantic role in the policy implies the opposite (e.g., A9270 'Noncovered item or service' directed by a non-denial sentence; the rule says cover, the semantics say exclude). Extractor silently reinterprets without escalation. | When the rule and the policy's evident semantic intent diverge, surface the discrepancy as a borderline Plan-turn decision; do not silently reinterpret. The extractor records what the policy says; the SME resolves rule-vs-semantic conflicts. **Related sub-principle:** denial-language phrasing on a coded reference triggers the denial polarity even in descriptive/structural usage — see §Polarity. |
| **code without context** | Extracting a bare code with no governing sentence recorded. | Manifest requires `governing_text` for every code. |
| **manifest count drift** | Verification counts in the Plan-turn manifest hardcoded as literals (e.g., `clinical_concepts: 25`) rather than computed from list lengths, allowing the count to disagree silently with what Generate produces from the canonical list. The list contents — not the count — are authoritative. | Derive every `verification.counts` value via `len(list)` in the manifest builder; cross-check the printed counts against the list lengths at Plan-turn output and surface any mismatch immediately. |
| **code invention** | Assigning a code to a clinical concept that has none. | Never guess. The concept is captured as a `gem:ClinicalConcept` individual; no code is invented. |
| **premature concept structuring** | Asserting `skos:broader`/`narrower` or merging synonyms during extraction. | Clinical concepts are a flat list; hierarchy is a later human-reviewed pass. |
| **consolidation-by-similarity** | Proposing reuse of an existing concept because it "obviously means the same thing" as a policy's differently-phrased term, thereby collapsing two phrasings into one individual at extraction time. The ontology's purpose is to catalog every way a meaning is expressed in policy text and provider notes, not to reduce the number of individuals; consolidation is destructive at this stage. | Strict-match rule: reuse only when the policy's wording matches an existing concept's prefLabel exactly (or near-exactly — trivial case/punctuation differences only). Different phrasing — a word dropped, a different noun, plural vs. singular, acronym vs. full-form when the existing prefLabel uses only one of those — defaults to mint, regardless of how clear the equivalence seems. See "Catalog phrasings; don't consolidate them" in Clinical Concepts. |
| **collision-reuse overreach** | Treating a URI collision as evidence of conceptual identity when the existing label and the new singular-normalized label differ by more than plurality (e.g., two distinct concepts happen to camelCase to the same string). | Singular-normalization rule (§Clinical Concepts): URI-collision reuse applies only when the existing label matches the new singular label except for plurality. Other collisions are surfaced as borderline decisions for SME review, never silently consolidated. |
| **credential routing by frequency** | A licensed credential link is routed to the most-linked credential individual (e.g., `credentialTreatingPractitioner`) by default, despite the source phrase naming a different role (e.g., "treating clinician"). | Routing rule (§Provider Credentials): the link goes to the individual whose `gem:prefLabel` matches the source phrase exactly. Note the verbatim phrase in the Plan-turn manifest. Never default by frequency. |
| **missed term-of-art alias** | Failing to recognize a regulatory parenthetical that aliases one credential phrase to another (e.g., "the term 'X' is defined in §… as 'Y'"); applying the routing-by-source-phrase rule naively to only the surface phrase, missing the additional licensed credential the policy explicitly hands the reader. | Term-of-art alias rule (§Provider Credentials): a regulatory parenthetical that aliases credential phrases licenses **all** aliased phrases as credential mentions; each is minted/reused as its own credential individual and linked from the citing policy. |
| **schema/instance bleed** | Putting instance data in the schema file or new terms in the instances file. | Three-artifacts table; strict separation. |
| **silent term creation** | Adding a class/property without user approval. | Class-creation governance; Plan-turn approval gate. |
| **reference without worklist** | Creating a `gem:referencesPolicy` link but not adding the worklist entry (or vice versa). | "Two outputs per discovered policy reference" — always both. |
| **scope creep** | Modeling thresholds, Groups, jurisdictions before the checkpoint. | First-policies scope discipline: log as deferred proposals. |
| **re-logging a promoted group** | Logging a concept group as a deferred proposal when it has already been promoted to a schema class (e.g., `gem:QualificationGroup`). | Pre-extraction step 2: enumerate promoted classes first; model promoted groups as individuals, never re-log them. |
| **schema source-doc bleed** | Minting a `schema:Book` source-document individual or declaring the `schema:` prefix in a GEM file (a habit carried over from the Sherlock guide). | GEM has no source-document individuals; `dc:source` is the URL (policies) or the policy URI (other individuals). See `gem_turtle_style_guide.md`. |
| **external-code namespace divergence** | Minting `gemi:hcpcs*` (or `gemi:icd10*`) reference URIs for external codes while other policies correctly use the external namespace (`hcpcs:`, `icd10:`) per §303 — producing two different URIs for the same external code. Cross-policy SPARQL queries on the external IRI silently miss the divergent policies. | §303 governs external-code namespaces: HCPCS uses `hcpcs:`, ICD-10 uses `icd10:`. Read it before any extraction with external codes; never infer the namespace from prior policies' practice. A divergence found in prior extractions is logged as a backfill candidate, not propagated. |
| **partial-read concealment** | Presenting a plan as complete when sections were skipped. | Honest-reporting principle; declare incomplete reading. |
| **misreported zero extraction** | Treating a deliberate "reviewed, no action taken" result as an unprocessed stub or an under-extraction — or the reverse, leaving a genuinely unread policy looking "reviewed." | Populate the stub in place with a description that explicitly records the deliberate zero outcome; `policies_processed` increments; the checkpoint states the zero is deliberate. See "The 'reviewed, no action taken' outcome." |
| **transmittal mistyped as pointer** | Minting a coverage-manual or claims-processing transmittal as a bare `owl:NamedIndividual` reference pointer instead of typing it as `gem:TransmittalPolicy` at first citation. Reverses the S41 + S45 methodology shifts. | Default-type rule (§Transmittals): every transmittal — including Pub. 100-04 (Claims Processing Manual) and Pub. 100-02 (Benefit Policy Manual) — is minted as `gem:TransmittalPolicy` at first citation, with `gem:nextPlannedStep = gem:planPromote`. Program Memoranda use `gem:ProgramMemorandumPolicy`. |
| **skipped change-propagation observation** | Failing to record the change-propagation observation when a transmittal is cited or extracted, losing the finding of whether the transmittal's claimed change has landed in its affected policy. | Observation rule (§Transmittals): record observation in the `change_propagation_observation` manifest field for every transmittal cited or extracted; observation is best-effort but skipping it loses the finding. |
| **unpromoted stub after extraction** | A fully-extracted policy's block left nested in its first-citing policy's POLICY STUBS sub-section, or stub promotion deferred to a separate later cleanup pass rather than completed during the stub's own Generate turn. The "populated in place" language in Turn 2 step 2 governs stub population only, not the stub-to-extracted promotion. | Stub-promotion rule (§Two-Turn Workflow → Turn 2): promotion to a top-level section is part of the stub's own Generate, not a deferred task. Verify at Generate completion that the promoted policy has its own `# === POLICY: <ident> ===` banner and that the original stub location under its first-citing policy is collapsed. |
| **unauthorized ontology version change** | Editing `owl:versionInfo` on `gem:gemOntology` without explicit user request. The version field is user-controlled and records the user's published-to-leadership state, not a per-session bookkeeping value. (Recurrence: a prior session bumped 0.0.5 → 0.0.6 without authorization; S42 found the value still wrong and bumped again to 0.0.7 before being corrected.) | Never edit `owl:versionInfo` without direct user request. The value persists across sessions unchanged. |
| **bundled approval questions** | Surfacing multiple borderline decisions in a single message rather than walking them iteratively, forcing the user to track several unrelated decisions at once. Applies to Plan turns, checkpoint reviews, skill refinements — any multi-decision interaction. | One-question-at-a-time rule (§Core Principles #9). Present each borderline as its own question; await the answer before asking the next. |
| **new vocab family born outside the mirror** | A new controlled-vocabulary family (class + property + members) is minted in `GEM_ontology.ttl` with `gem:llmDetailedDefinition` on its members, and `gem_llm_annotations.json` silently omits it. `gem_audit.py`'s `LLM_ANNOTATED_VOCAB_CLASSES` is a **hand-maintained tuple**, not a derivation: new *individuals* in a listed family flow into the mirror automatically, a new *family* does not. Nothing fires — `llm_annotation_drift` compares the mirror against the classes it was told about, so a family it was never told about cannot drift. The mirror stays green while being incomplete, which is the same shape as the S144 dead-check class: a benign default indistinguishable from a correct one. Canonical instance: `gem:SourceAvailability` (S156), minted one session after the S140 checkpoint recorded "no families pending" — a claim the tuple, not the graph, was answering. | **New-family checklist:** minting a controlled-vocabulary family is *five* edits, not one — (1) the class, property and members in `GEM_ontology.ttl`, with each member's `gem:llmDetailedDefinition` **verbatim** from its governing enumeration's per-value text (the `_meta` sync_note contract; assert it, do not eyeball it); (2) `LLM_ANNOTATED_VOCAB_CLASSES` in `gem_audit.py`; (3) the autofix run that regenerates the mirror; (4) `_meta.coverage` / `_meta.sync_note` rewritten **through** `_serialize_llm_annotations`, never by hand; (5) a `gem_reference.md` section. Verify by count: the mirror's entry total must rise by exactly the number of annotated members added. The standing fix — derive the class list as "every class with ≥1 individual carrying `gem:llmDetailedDefinition`" — is handoff §4 item 30. (Rule established 2026-07-17, Session 156.) |
| **over-escaped literal** | A string literal in a `.ttl` file is hand-escaped in the generator's source and escaped **twice**, so the literal's *value* carries a stray backslash (`\"a thing\"` where the author meant `"a thing"`). **The file parses**, SHACL conforms, the triple count and the predicate are both right; only the rendered text is wrong, so every instrument in the verification stack reports success. Under-escaping is the benign twin — it terminates the literal early and fails to parse immediately. Canonical instances: `credentialAttendingPhysician` and `credentialDoctorOfMedicineOrOsteopathy` (S41), `conceptSevereCardiacCondition` (S155) — undetected for up to 116 sessions. | **Escape at emit time; authors write plain text** (see §Session Close → *Emitter contract*). The `literal_escape_artifact` audit check (S157, YELLOW, autofixable) is the standing guard: it flags a three-backslash-before-quote sequence, computes the repair, **parse-probes the repair at detection time**, and downgrades to RED offering no autofix if its own repair does not parse or does not remove the artifact. Never hand-apply an escape repair — the repair is the same class of error as the defect, and S157 wrote that bug on the first attempt. (Rule established 2026-07-17, Session 157.) |
| **author-held line endings** | An emitter joins a multi-line block's lines with `\n` and the blocks with `\r\n`, so a `.ttl` file that requires CRLF throughout acquires lone-LF endings. **The file parses**, rdflib round-trips it, the set-diff is clean and the predicate histogram is perfect; the defect is invisible to every instrument except one. Sibling of *over-escaped literal* and of the predicate-blind mass-conservation proof: in all three the author held a property of the emitted bytes that the emitter should have held. Canonical instance: S158's NCD 280.16 section, **223 lone-LFs in a file that had zero**, written one session after the emitter contract centralised escaping and nothing else. | **The emitter owns the emitted bytes** (see §Session Close → *Emitter contract*): normalise line endings for the whole emitted region in one place, behind an assertion that no `\r` is authored above it. The `formatting` audit check is the standing guard — **RED, no autofix**, on any lone-LF in a TTL file (self-test V15) — so this one is caught before it lands; the contract is what stops the cycle being spent. | **URI collision (duplicate-mint)** | A Generate step mints new individuals at URIs that already exist as subjects in the instances file. The new triples merge silently with the existing definitions at the graph level — a single URI accumulates multiple `prefLabel` strings and multiple `description` strings, both of which are at-most-one-per-URI. (Multiple `dc:source` values on one URI are NOT a collision signal — provenance is legitimately multi-valued when an individual is referenced from more than one policy.) rdflib accepts the merge; the file parses; the graph's structure no longer matches its intent. The catalog-by-default principle (each distinct phrasing of a concept gets its own URI) is broken when a duplicate-mint conflates two distinct phrasings into one URI. Canonical instance: TN 2476's S49 Generate minted 10 specialty-code credentials whose URIs collided with 3 pre-existing NCD 210.1 credentials (identical local names, distinct provenance, distinct `prefLabel` and `description` strings). | **URI collision pre-flight audit rule:** before any Generate step that mints new individuals, audit every proposed URI against the instances file. **Three directions.** Forward audit — each proposed new URI must NOT match an existing line of the form `^<uri>\s+a\s+gem:`. Inverse audit — each proposed reuse URI MUST match (protects against typo-induced dangling references). **Retiree audit (S146)** — each proposed new policy URI `gemi:<x>` must ALSO be checked against `gemi:<x>_DELETED`. A hit is *not* a forward-audit collision (the bare URI is genuinely free, by design — see `gem_reference.md` §5.3), which is exactly why the first two directions miss it: §5.3 leaves the bare URI unreserved so a *different* future policy at the same section identifier has somewhere clean to land, and a mint that is the SAME policy as the retiree consumes the reservation for the one case it was not for. Halt and ask which it is; only a genuine CMS identifier reuse may take the bare URI. Guarded after the fact by the `deleted_twin_collision` audit check, but the pre-flight is where it costs nothing. Halt the Generate if any check fails; surface collisions as borderline Plan-turn decisions. **Cardinality conventions for the predicates that DO accumulate at a single URI:** `dc:source` is legitimately multi-valued (one value per source policy referencing the individual); `prefLabel` and `description` are at-most-one-per-URI (a single canonical label; a single coherent description). When a slipped-through collision yields multiple `prefLabel` triples, retain one as canonical and demote the rest to `skos:altLabel`. When multiple `description` triples exist, merge them in place into one prose description and review for semantic coherence. (Rule codified 2026-06-12, Session 50, after S49 TN 2476 duplicate-mint incident.) |
| **SHACL value-class encoding mismatch on code-namespace ranges** | A SHACL coverage Generate uses `sh:class <RangeClass>` uniformly across all object-property ranges, including ranges (`gem:HCPCSprocedure`, `gem:HCPCSmodifier`, `gem:ICDdiagnosis`, `gem:ICDgrouping`) whose individuals are typed by external BioPortal-conversion queries (`gem_hcpcs_conversion.rq` and ICD equivalents) and are NOT loaded into the audit-time validation graph. Canonical instance: S83 Cycle B's Phase 4 launch broke `phase3_provenance_reciprocity`'s implicit two-node-loop assumption (the rule expected `<P> hasPolicyRule <PR>` ⇒ `<PR> dc:source <P>` between the same two nodes; Phase 4's triangle architecture has `dc:source` and `hasPolicyRule` on different edges between three nodes). 6 RED findings surfaced post-Generate, requiring a Cycle C rule-generalization pass to clear. | **Audit-script gap analysis rule:** at Plan time, when a session changes ontology semantics, explicitly survey `gem_audit.py`'s encoded rules — by function and by category tag — for any whose docstring or implementation depends on the prior schema state. | **self-test fixture encodes the spec, not the corpus** | A check parses a real project artifact (a handoff, a SKILL.md sentence, a TTL header) with a regex, and its self-test variant *synthesizes* that input from the format as documented rather than sampling the format as actually written. Where the two diverge, the regex matches the fixture and nothing else: the variant passes, the suite reports all-green, and the check silently does no work on every real run. The silence is what makes it survive — the non-match path returns a benign default (`None`, `[]`) indistinguishable from a legitimately empty input, so the check reports clean precisely because it is dead. Note the inversion of the usual risk model: the suite's green is not weak evidence here, it is *anti*-evidence, because the fixture and the code drifted together away from reality. Canonical instances, both found S144 and both live for an unknown number of sessions: (i) `check_empirical_counts` required the handoff title `# GEM Policy-Extraction Session <N> Handoff` while every real handoff is titled `# GEM Policy-Extraction Handoff — Session <N> (<date>)`, so the empirical-counts session marker never advanced and the sentence would have kept reading "as of S138" beneath current counts (hand-patched at S143, opened as S143 §4 item 2); (ii) `parse_handoff_section_4` required §4 items shaped `**(a) Title**` while every real handoff writes `N. **Title**`, so `check_handoff_drift` — audit category 11, the guard against stale §4 framings — returned zero findings on every real handoff it ever ran against. V18/V19 and V33 synthesized the unused forms in both cases. | **Corpus-fixture rule:** a self-test variant for a check that parses a real artifact builds its fixture in the form the corpus actually uses. A form the corpus does not use may only ever be an *additional* variant pinning back-compatibility (V42, V44); it is never the baseline. **Inert-precondition rule:** where a parser's non-match returns a benign default, that path must raise a YELLOW rather than return silently — the check must distinguish "nothing to check" from "found nothing to check with." Both S144 repairs carry one (`detect_handoff_session` → YELLOW when a handoff is present but its title declares no session; `_section_4_inert_findings` → YELLOW when §4 carries bolded items but the item regex matched none). **Regression-test rule:** a variant written to pin a repaired parser must be *verified to fail against the pre-repair script* before it is trusted; a variant that passes both is coverage, not a regression test, and cannot show the repair did anything (S144 ran both scripts over the same fixture data to prove V33/V41/V43/V45 fail pre-repair). **Generalization:** when one instance of this class is found, sweep the whole script for the silent-return-on-non-match shape rather than patching the one site — that sweep is what turned up instance (ii). (Rules established 2026-07-14, Session 144.) |
| **a block-extent claim decays with every append** | A comment asserts where a machine-maintained region of a file *ends* — "this block extends to end-of-file", "everything below this header is auto-generated", "strip from here to EOF" — and the claim is true only until the next append. Nothing enforces it, so the file grows past it and the comment quietly becomes a lie. The claim is harmless right up to the moment someone acts on it, at which point it is destructive: the region's regeneration procedure deletes everything the stale boundary swept in. Two live instances found at S145 in `GEM_policy_instances.ttl`, both created by the ordinary convention of inserting new policy sections above the materialized `gem:refersToCodeGroup` block: (i) the BEGIN marker claimed the block ran to EOF, false from S131 onward, with 49 hand-authored transmittal/CR stubs inside the claimed span; (ii) a banner carrying the same claim had been pushed ~1,100 lines above its own block by successive promotions and so claimed 11 hand-authored policy sections as auto-generated. Note the mechanism differs from the S144 row above — no regex, no fixture, nothing drifted in *code*; the file simply grew, and a positional claim is falsified by growth alone. | **Delimit, do not describe.** A machine-maintained region gets an explicit opening AND closing marker; its extent is the span between them and is never expressed as a position relative to the file (EOF, "below", "the rest of"). **Guard the span.** A delimiter is a claim like any other until a check enforces it: `codegroup_block_extent` (S145) asserts exactly one marker of each kind in order, nothing but generated lines inside the span, and no generated line outside it — the S144 inert-precondition rule applies, so missing markers are YELLOW rather than a silent pass (that path is what fires on the pre-S145 file, whose old marker text the guard does not recognize). **Correct every copy.** The claim lived in four places — two markers, `SKILL.md`'s regeneration procedure, `gem_reference.md`'s prose — and a repair that misses one leaves the hazard reachable. **Generalize the sweep:** when a positional claim is found stale, grep the corpus for the whole family (`to EOF`, `end-of-file`, `everything below`, `do not hand-edit`) rather than fixing the reported one; that sweep is what turned up instance (ii) and the stale "near end-of-file" locator on the Retroactive Assignment section (harmless — descriptive, with no strip procedure attached — and dropped at S145). (Rules established 2026-07-14, Session 145.) |
| **a stale cross-reference mints a duplicate of a retiree** | A policy's cross-reference names a section that has since been deleted, and the extraction mints it as a fresh bare stub — silently creating a second entity for a real-world document that already exists in the graph at its `_DELETED` URI, and consuming the standard URI that `gem_reference.md` §5.3 reserves for a *different* future policy at that identifier. Nothing in the source catches it either — the citing policy's text is verbatim correct; it is *reality* that moved. | **a predicate carries a second question** | A predicate is asked to answer two questions at once, and answers a different one depending on which subject it is asserted about. It never looks broken: every value is defensible under *one* of the readings, so a reader who holds the other reading sees a contradiction that isn't there, and a reader who holds neither reads the values as answers to whichever question the name suggests. **Three signals, any one of which is sufficient.** (i) *The definition contains both readings, unreconciled* — `gem:isInEffect`'s description opened document-level ("whether a CMS policy document is currently in effect") and closed version-level ("to give version-currentness a graph home"), and its scoping note hedged with the giveaway word *"coverage/version currentness"*. (ii) *A default-assignment table assigns the value rather than the definition* — `gem_reference.md` §2k's row *"Other stub, `is_current=false` → `planNone` / `false`"* is what put `false` on 37 documents; the property's own definition never licensed it, and the discriminator turned out to be stub-vs-extracted, not anything the name means. (iii) **A caveat in a cardinality note is a confession.** `gem:isInEffect`'s said *"a transmittal that revises multiple policies carries a single gem:isInEffect that may be correct for one target and not another; read it as its status relative to its primary/most-recent target, not a universal claim"* — that is the property stating in its own definition that it cannot answer for 121 of its subjects. `gemi:tn48NCD` revises twenty policies; one boolean, twenty answers. **How it gets in: a rename.** S45 renamed the worklist's `is_current` field to `gem:isInEffect` and **kept all 327 answers to the old question**. Renaming a predicate is a semantic change, not a cosmetic one — currentness is a fact about *now* and fits a boolean; legal force is a relation between a version and a date of service and does not. The defect stood 113 sessions, produced two wrong NCD counts (S150's and S158's, wrong for different reasons), and was invisible to parse, SHACL, mass conservation and the whole self-test suite, because every value was individually defensible. | **Name the question, then check every subject answers it.** A predicate's definition states the *one* question it answers and, explicitly, the neighbouring questions it does not — `gem:isInEffect` now names three (retirement in place, rescission/supersession, version currentness) and a fourth it is most likely to be mistaken for (claim applicability). **Never write the caveat — fix the predicate.** A cardinality note that tells the reader how to *cope* with a wrong value is the point at which the second question is already in; the note is cheaper to write than the fix, which is why it survives. **A relation does not fit a boolean.** If answering the question requires an argument the subject does not carry (a date of service, a target), the predicate cannot hold the answer, and pinning the missing argument to an implicit default (*now*, *the primary target*) buries the defect rather than solving it — publish the argument and let the consumer join. **On any rename, re-derive the values; do not inherit them.** Two predicates are not coextensive because one name replaced the other. (Rules established 2026-07-17, Session 159, resolving `deferred_proposals[97]`; the full definition and its history are in `gem_reference.md` §2k → *What `gem:isInEffect` means*.) |
| **an abstract parent reads as unused** | A usage census counts asserted triples per term and reports **0** for a predicate or class that is only ever asserted through its descendants. Measured at S197: `gem:coversCondition` 0 asserted against 3,252 through `gem:exclusivelyCoversCondition` and its two sub-properties; `gem:refersToHCPCSprocedure` 0 against 409; `gem:appliesWhenCode` 0 against 91; `gem:hasAnchoredCodingScope` 0 against 29; and the classes `gem:CMSpolicy` 0 direct against 592 and `gem:AnchoredCodingScope` 0 against 29. **The number is real, which is why it survives review** — what is wrong is the question it answers, and nothing in the count says so. Canonical instance: the S140 60-policy schema-health review counted this way ("from the asserted graph, no inference"), filed `deferred_proposals[92]` naming `gem:coversCondition` and `gem:refersToHCPCSprocedure` as retirement candidates, and set a standing trigger to revisit *"if still 0-usage at a materially larger corpus"*. At the S197 100-policy review that trigger fired on the identical false reading, and acting on it would have retired a super-property carrying thousands of inferred triples. Note the corpus was not silent: both terms already carried a `gem:llmScopingNote` saying they hold no direct triples. The graph told the truth; the review method did not read it. | **Count closure-aware.** A term's usage is its own assertions plus every descendant's under `rdfs:subPropertyOf` / `rdfs:subClassOf`. Report both numbers; never the direct count alone. **Zero direct use on a parent is the expected state, not a finding.** A parent earns its place in cohort-level analysis, where a query generalises over descendants instead of enumerating them — and that use produces no instances by construction, so instance counts can neither evidence it nor disprove it (Tom, S197). Retiring a parent therefore needs an argument about the generalisation it supports, never a census. **Read the term's own annotations before proposing anything about it.** Every abstract parent carries a `gem:llmScopingNote` stating that direct assertion is zero by design; write one on any new parent. (Rule established 2026-07-24, Session 197.) |

## Iterative Improvement

This skill is a living document. **After every policy — not only at the 20-policy checkpoint — review the pass for refinements.** Each policy read is an opportunity to discover a methodology improvement; the Verification Checkpoint of every policy concludes with an explicit question: *did this pass reveal a refinement, a new failure mode, or a missing rule that should be promoted into the skill?* If yes, propose the skill edit to the user as its own mini Plan/Generate step (the edit is reviewed and approved like any other change).

When promoting a refinement, place it correctly:

- `SKILL.md` (this file) — durable methodology rules and cross-cutting principles.
- `gem_reference.md` — GEM terms, URI schemes, and naming conventions.
- `gem_rule_categories.md` — rule categorization conventions and axis-1/axis-2 vocabulary.
- `gem_turtle_style_guide.md` — Turtle serialization rules.
- `manifest_format.md` — Plan-turn manifest structure and field semantics.
- `worklist_schema.md` — worklist structure and maintenance rules.

Session-specific state (progress, queue, current file signatures) stays in the handoff document and is **not** promoted to the skill. A convention carried only in successive handoffs is one missed copy forward from being lost — promote it.

At each 20-policy checkpoint, additionally review: schema health, worklist size, the deferred-proposal backlog, promotion of deferred concept groups seen in 3+ policies, CLAUDE.md's standing rules, and (where applicable) a decision on batch size for the remaining work. **The schema-health usage census is closure-aware** — a term's usage is its own assertions plus every descendant's, and a parent reading zero direct assertions is expected rather than a finding; see *an abstract parent reads as unused* in Common Failure Modes before proposing any term for retirement.

Standing maintenance tasks:
1. Record any new failure mode in the Common Failure Modes table.
2. Promote deferred concept groups the user approves into `gem_reference.md` and the taxonomy.
3. Refine the document-type and code-context rules as new policy formats appear.
